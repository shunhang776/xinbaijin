# 白槿 v2 → AI Native 转型草案

> 不是"加一个 AI 功能"，是让 AI 从代码生成层渗透到运行时层。
> 目标：系统能发现自己哪里不对、能自己修、能自己变好。

---

## 当前状态：AI-Generated，不是 AI-Native

```
现状：
  代码层 ─── AI 写的 ─── ✅
  运行时 ─── 传统运维 ─── ❌ (端口检查 + 进程重启)
  质量层 ─── 无反馈 ───   ❌ (不知道回复好不好)
  演进层 ─── 人等 bug ───  ❌ (死代码躺了一周没人发现)
```

---

## 阶段一：自感知（最小成本，最大收益）

**目标：系统知道自己在干什么。**

### 1.1 模块调用链自动审计

当前死代码是人工 grep 发现的。改成每次启动时自动扫描。

```python
# 在 startup 中加一个 audit() 调用
# 遍历 src/*.py → 解析 AST → 检查每个公开函数是否被引用
# 未引用的记入 logs/dead_code.log，同时在 /health 中暴露
```

```
GET /health 返回值增加：
{
  "dead_modules": ["ai_lss", "context"],   ← 只提醒，不自动删
  "unused_functions": {"feedback.py": ["assess"]},
  "last_audit": "2026-06-07T12:00:00"
}
```

**工作量**：~50 行 Python AST 遍历，加一个 startup 调用。

### 1.2 结构化日志

当前日志是散落的 `logger.info("xxx")`，无法被程序消费。

```
当前：2026-06-07 12:25:44,212 - baijin.main - INFO - 白槿 v2 启动完成
改为：{"ts":"...","src":"main","event":"startup_complete","modules":7,"dead":0,"ms":12300}
```

不改日志格式，加一个旁路：关键事件同时写一份 JSON 行到 `logs/events.jsonl`。

**工作量**：一个 `log_event(name, data)` 工具函数，在所有关键节点调用（启动完成、消息处理、异常、重启）。

### 1.3 对话质量度量

每次回复后，等用户的下一条消息来判断质量。

```
用户回复长度 ≥ 5 字 → 上一轮 "好"
用户回复 = "？" / "啥" → 上一轮 "差"（没讲清楚）
用户沉默 > 30 分钟 → 上一轮 "一般"（没激发继续聊）
5 分钟内连续回复 → 上一轮 "很好"
```

这些信号写进 `data/quality.jsonl`，形成可查询的质量数据集。

**工作量**：在 `_post_process` 的 feedback 模块中补一个 `quality_log`，~30 行。

## 阶段二：自修复（需要 AI 介入运行时）

**目标：系统出问题能自己尝试修，不只是重启。**

### 2.1 分级故障响应

当前 v2_ops 的逻辑：检测异常 → 无脑重启。应该分级：

| 故障类型 | 检测方式 | 响应 |
|---------|---------|------|
| 端口不通 | socket | 重启 main.py |
| /health 返回异常 | HTTP 200 + status≠ok | 重启 main.py |
| 单个模块挂了 | /health 返回 embedding=false | 尝试重新 init_embedding，不重启 |
| 回复质量连续差 | quality.jsonl 最近 10 条分 < 0.3 | 调整 system prompt 参数 |
| DeepSeek API 连续 429 | 请求日志 | 降速，增加重试间隔 |
| 内存/CPU 持续高 | psutil | 触发 ai_lss G1 档位 |

**工作量**：改造 v2_ops 的 `_tick`，~50 行。

### 2.2 运行时配置自调

某些参数不应该写死在 config.yaml，应该根据运行时数据自动漂移。

```
当前 config.yaml 的静态值：
  deepseek.max_tokens: 500       → 根据用户平均消息长度自动调整
  memory.top_k: 10               → 根据检索命中率调整
  proactive.MIN_INTERVAL: 3600   → 根据用户响应率调整
```

做法：在 `data/` 下加一个 `auto_config.json`，每次巡检时如果发现连续 N 次信号指向同一方向，就微调参数。

```
if 最近 20 次回复全部 < 100 字 → max_tokens -= 50
if 最近 10 次检索无命中 → top_k += 5
if 主动消息连续 3 次无回复 → MIN_INTERVAL *= 1.5
```

**工作量**：v2_ops 的 `_tick` 中加一个 `_auto_tune()`，~40 行。

### 2.3 故障根因日志

当前异常日志只有 `type(e).__name__: e`。加上运行时上下文快照：

```python
def _crash_snapshot():
    return {
        "ts": time.time(),
        "traceback": traceback.format_exc(),
        "modules": health_check_snapshot(),
        "last_5_messages": list(_history)[-5:],
        "memory_count": memory.count(),
        "cpu": psutil.cpu_percent(),
        "ram": psutil.virtual_memory().percent,
    }
```

重启前把这个快照写入 `logs/crashes/`，供事后分析。

**工作量**：在 v2_ops 的 `_restart_service` 前调用，~25 行。

## 阶段三：自演进（最激进，但也是最"AI Native"的）

**目标：AI 不只是写初始代码，而是持续参与系统的改进。**

### 3.1 对话驱动的模块迭代

每条对话都是测试用例。失败的回复是 bug report。

```
流程：
  用户消息 → LLM 回复 → 用户后续行为（沉默/追问/纠正）
                                    │
                    ┌───────────────┘
                    ▼
            质量评估 (AI 判断用户是否满意)
                    │
            ┌───────┴───────┐
            ▼               ▼
       满意 → 入库样本    不满意 → 入库 bad_cases
                                      │
                                      ▼
                              每周汇总 bad_cases
                              让 AI 分析模式
                              生成改进建议
                              人工审核 → 更新 rules.json / style_gene
```

当前 sample.py 只存好样本。加一个对称的 bad_cases 收集。

**工作量**：`data/bad_cases.jsonl` + 一个分析脚本，~60 行。

### 3.2 System Prompt 的 A/B 测试

System Prompt 是五层拼接。哪层对回复质量影响最大？不知道。

```
在 prompt.py 中加一个实验模式：
  50% 流量 → 完整五层 prompt（对照组）
  50% 流量 → 去掉示例层（实验组）
  
  对比两组的 quality 分数
  如果去掉示例层没影响 → 可以简化
  如果去掉后质量暴跌 → 示例层是关键
```

不需要真的 50/50 分流——可以在连续对话中交替使用，用 20 轮后的平均质量分做对比。

**工作量**：prompt.py 加一个 `experiment_mode` 开关，~20 行。

### 3.3 死代码自动归档

第一阶段的审计发现死代码后，不应该是人在终端敲 `rm`。

```
发现 dead_module → 
  1. 写入 logs/dead_code.log
  2. 等待 7 天
  3. 7 天后仍未接入 → 自动移到 archive/ 目录
  4. /health 报告 "archived_modules"
```

**工作量**：在 v2_ops 的定时任务中加一个检查，~30 行。

## 优先级排序

按投入产出比排：

| 优先级 | 阶段 | 项目 | 工作量 | 理由 |
|--------|------|------|--------|------|
| P0 | 一 | 结构化日志 | 20 行 | 后面所有阶段的数据基础 |
| P0 | 一 | 对话质量度量 | 30 行 | 后面所有优化的判断依据 |
| P1 | 一 | 模块调用链审计 | 50 行 | 杜绝死代码反复出现 |
| P1 | 二 | 分级故障响应 | 50 行 | 减少无脑重启，降低故障影响 |
| P2 | 二 | 故障根因快照 | 25 行 | 出问题时不用猜 |
| P2 | 二 | 配置自调 | 40 行 | 让系统越跑越适配用户 |
| P3 | 三 | 对话驱动迭代 | 60 行 | 需要积累足够数据才有效 |
| P3 | 三 | 死代码自动归档 | 30 行 | 锦上添花 |
| P4 | 三 | A/B 测试框架 | 20 行 | 好玩但非刚需 |

## 不需要做的事

- **不做知识图谱/元记忆那一套**——旧系统的教训，Chroma + SQLite 够了
- **不做自动写代码**——AI 生成模块然后自己接入，风险太高，人的审核节点必须保留
- **不做实时监控面板**——单用户系统，/health 端点 + 日志就够了

---

## 从哪开始

今天就能做的：结构化日志 + 对话质量度量。两个加起来不到 60 行代码，但它们是后面所有阶段的眼睛——没有数据，自修复和自演进都是空谈。
