# 白槿 v2 工程政策防腐机制

> 文档类型：工程治理政策、执行防腐制度与质量控制规范  
> 适用范围：白槿 v2 重构项目及其后续新增模块、迁移、发布、运维和政策变更  
> 适用对象：项目负责人、架构负责人、实现者、审查者、测试人员、验收者、发布负责人、运维人员及参与项目的 AI Agent  
> 依据文档：《白槿 v2 执行方案实际缺陷与系统性补救方案》  
> 政策目标：防止工程政策在执行过程中被弱化、曲解、绕过、形式化、数据化美化或通过例外逐步掏空  
> 核心原则：**任何“完成”“通过”“安全”“可回滚”的声明，都必须由可复现、可审计、可反证的证据支持**

---

# 一、制定背景

白槿 v2 的重构方案在架构设计、模块拆分、风险意识、灰度迁移、日志指标、生命周期和回滚等方面具备较强的工程基础，但实际执行过程已经暴露出一类比普通代码缺陷更危险的问题：

> 工程政策本身没有被直接否定，却在执行中被逐步替换成了更容易完成、更容易汇报、但无法证明真实目标已经实现的形式。

典型表现包括：

- 把“文件已生成”解释为“功能已完成”；
- 把“现有测试通过”解释为“设计合同通过”；
- 把“使用高推理档位审查”解释为“质量已经可靠”；
- 把“有回滚说明”解释为“已经具备真实回滚能力”；
- 把“1% 灰度”解释为“已获得足够生产证据”；
- 把“无报错”解释为“没有风险”；
- 把“文档已更新”解释为“文档与代码一致”；
- 把临时例外长期保留，最终形成默认路径；
- 在验收失败后修改测试或降低标准，再宣布通过；
- 由同一执行过程同时负责实现、测试、解释和验收；
- 使用测试数量、文件数量、提交数量等替代真实质量；
- 忽略数据迁移、索引、状态等有状态模块的回滚复杂性；
- 进度表持续标绿，而关键合同仍未满足。

这些问题说明，单纯增加规则、测试或审查次数并不能自动保证政策不被腐化。  
必须建立一套具有以下能力的工程治理机制：

1. 政策含义清晰，不能任意解释；
2. 执行权、审查权和验收权相互制约；
3. 阶段状态由证据生成，而非人工宣布；
4. 标准不能在验收时被静默降低；
5. 例外必须可见、可追踪、会自动到期；
6. 关键违规能够被工具直接阻断；
7. 所有完成声明都能绑定具体代码版本；
8. 历史记录不能被事后改写；
9. 高风险变更必须经过对抗性验证；
10. 政策本身也必须定期审查，避免失效或诱发错误行为。

# 二、政策防腐的定义

本制度所称“工程政策腐化”，是指工程政策在形式上仍被保留，但其实际约束力、目标或证据标准在执行过程中被削弱、转移或替代。

## 2.1 结果腐化

真实目标没有完成，但通过替代指标宣布成功。

例如：

```text
目标：公共 API 合同完整
替代：文件存在、单元测试数量增加
结果：公共 import 仍失败，但阶段标记完成
```

## 2.2 口径腐化

在执行中改变“错误”“完成”“回滚”“灰度”等词的含义。

例如：

```text
原定义：错误率包括未捕获异常和降级失败
执行口径：只统计 HTTP 500
```

## 2.3 证据腐化

使用无法复现、不绑定版本或不能证明目标的材料作为证据。

例如：

- 截图没有 commit；
- 测试日志来自旧版本；
- 手工汇报“运行正常”；
- CI 只在一个平台执行；
- 回滚只写文档，没有演练。

## 2.4 程序腐化

绕过原定的审批、审查或验收流程。

例如：

- 紧急发布长期常态化；
- 高风险模块不经过独立审查；
- 例外由申请人本人批准；
- 验收失败后由实现者直接修改验收标准。

## 2.5 指标腐化

为了让数据变好而优化统计方式，而不是优化系统质量。

例如：

- 删除失败测试；
- 将失败标记为 skip；
- 只报告平均延迟；
- 将降级响应排除出错误统计；
- 用测试数量替代合同覆盖。

## 2.6 文档腐化

文档与实际实现、测试和发布状态不一致，但仍作为决策依据。

## 2.7 例外腐化

临时豁免没有到期、没有补偿措施或不断续期，最终掏空规则。

## 2.8 权力腐化

同一主体同时拥有规则解释、执行、验收和例外批准权，导致缺少制衡。

# 三、治理目标

本机制不以“完全消除错误”为目标，而以以下能力为目标：

- 错误能够被尽早发现；
- 偏离政策能够被自动识别；
- 虚假完成难以生成；
- 例外不能静默存在；
- 高风险行为必须留下证据；
- 验收标准不能被临时改写；
- 有状态变更能够恢复；
- 决策责任能够追溯；
- 政策执行成本与风险相匹配；
- 政策本身可以被正式修订，但不能被私下绕过。

最终应形成以下闭环：

```text
政策定义
→ 合同冻结
→ 风险分级
→ 证据要求
→ 执行
→ 对抗审查
→ 自动门禁
→ 独立验收
→ 灰度与回滚
→ 审计
→ 复盘
→ 政策改进
```

# 四、基本治理原则

## 4.1 证据优先原则

任何状态声明必须有证据。

禁止仅凭以下表述标记完成：

- “已经处理”；
- “基本没问题”；
- “测试很多”；
- “人工看过了”；
- “模型深度复核过”；
- “应该能回滚”；
- “线上暂时没报错”。

可接受证据必须满足：

1. 绑定具体 commit；
2. 说明执行环境；
3. 命令可复现；
4. 输出完整；
5. 能直接证明对应条款；
6. 能被第三方重新执行；
7. 不依赖执行者口头解释才能成立。

## 4.2 权力分离原则

以下权力原则上不得由同一角色同时独占：

- 政策制定权；
- 政策解释权；
- 代码实现权；
- 验收标准修改权；
- 最终验收权；
- 例外批准权；
- 发布批准权。

小团队无法完全人员分离时，必须至少做到任务分离和时间分离。

## 4.3 默认拒绝原则

缺少证据时，默认状态不是“通过”，而是：

```text
未验证
```

未运行 Windows CI，不能写“跨平台通过”；  
未做回滚演练，不能写“可回滚”；  
未做干净安装，不能写“依赖完整”。

## 4.4 否决项优先原则

严重风险不能被综合分抵消。

以下任一项出现，阶段直接失败：

- 数据丢失；
- 密钥或隐私泄露；
- P0 缺陷未关闭；
- 核心合同测试失败；
- 真实循环依赖；
- 迁移不可恢复；
- 验收证据与 commit 不一致；
- 核心测试被删除、跳过或伪造；
- 回滚路径已知不可用；
- 生产安全红线被突破。

## 4.5 规则左移原则

保护某项合同的规则，应在该合同首次引入时启用，而不是等到项目后期。

## 4.6 最小权限原则

任何角色只获得完成职责所需的最小权限。

例如：

- 实现者不能直接将阶段改为“已验收”；
- 测试维护者不能单独批准删除关键验收测试；
- 发布者不能自行批准高风险例外；
- AI Agent 不能自行修改冻结政策并宣布符合新政策。

## 4.7 可逆优先原则

在无法证明安全前，优先选择可回滚、可双读、可双写、可重建的方案。

## 4.8 追加式审计原则

关键记录只能追加，不允许覆盖历史。

# 五、治理角色与职责分离

## 5.1 政策所有者

负责：

- 定义政策目标；
- 维护政策版本；
- 组织定期复审；
- 审批重大政策变更。

不得：

- 单独验收自己推动的高风险变更；
- 静默修改历史验收标准；
- 删除失败记录。

## 5.2 架构负责人

负责：

- 冻结公共合同；
- 审查模块边界；
- 审查依赖方向；
- 审批公共 DTO、Protocol 和 schema 变更；
- 判断是否触发架构级风险审查。

## 5.3 实现者

负责：

- 按冻结合同实现；
- 提交代码、测试和变更说明；
- 说明已知限制；
- 复现和修复缺陷。

不得：

- 单独宣布最终验收通过；
- 修改验收标准以适配当前实现；
- 隐藏失败路径；
- 自行批准自己的例外。

## 5.4 对抗审查者

负责主动寻找：

- 反例；
- 并发窗口；
- 不可恢复状态；
- 文档与代码偏差；
- 测试无效断言；
- 指标操纵空间；
- 安全绕过；
- 例外滥用；
- 回滚缺口。

其目标不是证明实现正确，而是尽量证明实现可能不正确。

## 5.5 测试与质量负责人

负责：

- 维护验收测试；
- 保证测试能在旧缺陷上失败；
- 维护 CI 矩阵；
- 审查 skip、xfail 和测试删除；
- 保证测试报告绑定 commit。

## 5.6 验收者

负责：

- 依据冻结标准判断通过或失败；
- 检查证据完整性；
- 不参与实现细节辩护；
- 对缺少证据的项目标记“未验证”。

不得：

- 在验收阶段临时降低标准；
- 使用投入成本作为放宽理由；
- 用平均分抵消红线失败。

## 5.7 发布负责人

负责：

- 确认发布门禁；
- 验证灰度和回滚；
- 记录发布版本；
- 在指标异常时执行停发或回滚。

## 5.8 审计者

负责：

- 随机抽查已完成项目；
- 检查例外；
- 检查状态证据；
- 检查历史是否被修改；
- 检查验收报告与实际 commit。

## 5.9 AI Agent 的特殊约束

AI Agent 可承担实现、测试生成、分析或审查任务，但必须遵循：

1. 同一次任务中，AI 生成代码后不得仅凭自身解释宣布最终通过；
2. 高风险模块必须由独立上下文或独立审查轮进行对抗审查；
3. AI 不得将“推理档位”作为通过证据；
4. AI 生成的测试必须通过缺陷复现验证；
5. AI 无权静默修改冻结政策；
6. AI 无权伪造命令、测试结果或环境；
7. 未实际执行的验证必须标记为“未运行”；
8. AI 结论必须区分事实、推断和建议；
9. 长任务必须保留中间产物与变更摘要；
10. AI 参与验收时，应读取冻结标准，而不是根据实现重新解释目标。

# 六、工程政策的标准结构

任何正式工程政策都必须包含以下内容：

1. 政策目标；
2. 适用范围；
3. 术语定义；
4. 责任角色；
5. 必须执行的动作；
6. 禁止行为；
7. 所需证据；
8. 验收标准；
9. 否决条件；
10. 例外流程；
11. 回滚要求；
12. 审计方式；
13. 生效时间；
14. 失效或复审时间；
15. 政策版本。

禁止只写：

```text
加强测试
保证质量
注意回滚
做好审查
```

政策应改写为可验收条款。

例如：

```text
所有 Phase 在标记为“已验收”前，必须在当前 commit 上通过 Linux 与 Windows CI；
测试报告必须包含 commit SHA、Python 版本、依赖锁 hash 和完整命令；
任一目标平台未执行时，状态只能为“未验证”，不得标记“跨平台通过”。
```

# 七、政策版本与冻结机制

## 7.1 版本化

政策采用语义化版本：

```text
Major.Minor.Patch
```

示例：

```text
1.0.0：首次生效
1.1.0：新增灰度样本要求
1.1.1：修正文案，不改变要求
2.0.0：改变阶段完成定义
```

## 7.2 冻结点

每个 Phase 开始前冻结：

- 设计合同；
- 验收指标；
- 失败判定；
- 测试清单；
- 目标平台；
- 回滚要求；
- 灰度样本；
- 责任角色。

## 7.3 变更政策

执行期间可以修改政策，但必须：

1. 提交正式变更记录；
2. 说明原条款和新条款；
3. 说明变更原因；
4. 说明风险；
5. 由非直接实现者批准；
6. 设定生效时间；
7. 不追溯性改写历史结果；
8. 重新评估受影响的已完成阶段。

## 7.4 禁止静默降低标准

以下行为视为政策违规：

- 删除失败测试后不记录；
- 将失败测试改为 skip；
- 修改阈值但不修改政策版本；
- 改变错误统计口径但继续使用原指标名称；
- 修改验收脚本后复用旧验收报告；
- 用新政策追溯性宣布旧失败为通过。

# 八、阶段状态防腐机制

## 8.1 状态模型

每个交付项使用以下状态：

```text
DRAFT
DESIGNED
IMPLEMENTED
UNIT_TESTED
CONTRACT_VERIFIED
INTEGRATED
FAULT_TESTED
CROSS_PLATFORM_VERIFIED
ROLLBACK_VERIFIED
ACCEPTED
CANARY
RELEASED
DEPRECATED
```

## 8.2 状态转换权限

| 状态转换 | 允许角色 |
|---|---|
| DRAFT → DESIGNED | 架构负责人 |
| DESIGNED → IMPLEMENTED | 实现者 |
| IMPLEMENTED → UNIT_TESTED | 测试负责人/CI |
| UNIT_TESTED → CONTRACT_VERIFIED | 验收者 |
| CONTRACT_VERIFIED → INTEGRATED | 集成负责人/CI |
| INTEGRATED → FAULT_TESTED | 质量负责人 |
| FAULT_TESTED → CROSS_PLATFORM_VERIFIED | CI |
| CROSS_PLATFORM_VERIFIED → ROLLBACK_VERIFIED | 发布负责人 |
| ROLLBACK_VERIFIED → ACCEPTED | 独立验收者 |
| ACCEPTED → CANARY | 发布负责人 |
| CANARY → RELEASED | 发布审批者 |

单一角色不得跨越多个关键状态直接修改为 RELEASED。

## 8.3 状态由机器证据生成

推荐建立：

```text
scripts/ops/check_phase_status.py
```

输出：

```yaml
phase: 1
commit: abc123
policy_version: 1.0.0
implementation: pass
unit_tests: pass
contract: fail
integration: not_run
fault_injection: not_run
linux_ci: pass
windows_ci: not_run
clean_install: fail
rollback_drill: not_run
p0_open: 2
p1_open: 7
accepted: false
```

Markdown 状态应由该文件生成。

## 8.4 禁止人工直接标绿

任何人不得只修改进度文档，将状态从“处理中”改为“完成”。

状态变更必须伴随：

- 证据文件；
- CI 链接或结果；
- commit；
- 验收者；
- 时间；
- 政策版本。

# 九、四道工程门禁

## 9.1 实现门

必须验证：

- 文件存在；
- 语法正确；
- import 可执行；
- requirements 完整；
- 类型检查通过；
- 没有占位实现；
- 没有导入时重型副作用；
- 没有明显死代码；
- 没有未授权依赖。

典型命令：

```bash
python -m compileall .
ruff check .
mypy core infra
```

## 9.2 合同门

必须验证：

- 公共 API；
- DTO 不变量；
- Protocol；
- 异常前缀；
- trace/span；
- 生命周期；
- 依赖图；
- 配置边界；
- 安全脱敏；
- 版本唯一真源；
- lint 规则。

合同门必须包含失败反例。

## 9.3 集成门

必须跑通最小真实纵向链路：

```text
request
→ trace
→ service
→ container
→ infra
→ database
→ Result
→ exception mapping
→ logging
→ metrics
→ shutdown
```

不得用全部 mock 替代真实集成。  
允许外部 API 使用 mock，但内部模块边界必须真实连接。

## 9.4 发布门

必须满足：

- P0 = 0；
- P1 = 0；
- Linux CI 通过；
- Windows CI 通过；
- 干净安装通过；
- 回滚演练通过；
- 灰度最低样本满足；
- 文档与 commit 一致；
- 安全红线通过；
- 没有核心 skip/xfail；
- 发布批准完整。

# 十、证据链管理

## 10.1 证据最小字段

每份验收证据必须包含：

```text
policy_version
project_version
commit_sha
branch
timestamp
operator
reviewer
python_version
os
dependency_lock_hash
command
exit_code
full_output
artifact_hash
```

## 10.2 证据等级

| 等级 | 说明 |
|---|---|
| E0 | 口头说明，不可接受 |
| E1 | 截图，弱证据 |
| E2 | 日志但未绑定 commit |
| E3 | 可复现命令并绑定 commit |
| E4 | CI 自动执行并保存产物 |
| E5 | 独立环境复现、签名和审计完整 |

关键门禁至少要求 E4。

## 10.3 证据保存

建议保存：

```text
artifacts/
  phase1/
    commit-abc123/
      test-report.xml
      coverage.xml
      lint.json
      mypy.txt
      clean-install.txt
      windows-ci.json
      linux-ci.json
      rollback-report.md
      acceptance.yaml
```

## 10.4 证据不可覆盖

同一 commit 的失败记录不能被删除。  
修复后应生成新 commit 的新记录。

# 十一、测试政策防腐

## 11.1 测试必须能失败

新增测试前应证明：

- 在缺陷版本上失败；
- 在修复版本上通过；
- 失败原因与设计合同一致。

## 11.2 禁止无效断言

禁止：

```python
assert condition or True
assert object is not None  # 当真正要求是脱敏、格式或行为
```

## 11.3 测试删除审查

删除或弱化以下测试必须双人批准：

- 公共 API；
- 数据一致性；
- 安全；
- migration；
- rollback；
- 生命周期；
- 跨平台；
- 错误码；
- trace；
- 并发。

## 11.4 skip 和 xfail

每个 skip/xfail 必须包含：

- issue 编号；
- 原因；
- owner；
- 到期日期；
- 解除条件。

到期后 CI 应失败。

## 11.5 测试数量不得作为主要指标

不得使用：

```text
测试从 262 增加到 400，所以质量提高
```

应统计：

- 设计条款覆盖率；
- 失败路径覆盖率；
- 变异测试得分；
- 缺陷逃逸率；
- 回归捕获率；
- 关键分支覆盖；
- 合同测试覆盖。

## 11.6 测试与实现隔离

高风险合同测试应由独立审查轮维护，不得完全由实现者自定义。

# 十二、指标防游戏化

## 12.1 多指标交叉

任何关键结论不得只依赖单一指标。

例如性能应同时检查：

- P50；
- P95；
- P99；
- 最大延迟；
- 吞吐；
- CPU；
- RSS；
- 线程数；
- 队列；
- 连接池等待。

## 12.2 禁止只报告平均值

平均值可能掩盖尾部故障。

## 12.3 错误分类

不得只报告“总体错误率”。

必须区分：

```text
crash
data_loss
security
unhandled_exception
5xx
timeout
fallback
circuit_open
degraded_response
business_rejection
migration_error
```

## 12.4 红线独立展示

以下指标必须独立展示，不得合并：

- 数据丢失；
- 安全事件；
- 未处理异常；
- 回滚失败；
- schema 不一致；
- 写入不一致。

## 12.5 指标口径版本化

任何统计口径变化都必须：

- 升级指标版本；
- 保留新旧口径对比；
- 不与旧数据直接混合；
- 记录变更时间。

# 十三、例外管理

## 13.1 例外申请字段

每个例外必须包含：

```text
exception_id
policy_clause
requester
owner
reason
business_impact
technical_risk
compensation
scope
start_at
expire_at
review_at
approver
removal_plan
```

## 13.2 例外规则

- 必须有到期时间；
- 默认最长不超过一个迭代；
- 不得由申请人本人批准；
- 不得无限续期；
- 续期必须重新评估风险；
- 到期未关闭，CI 或发布门禁自动失败；
- 例外必须在状态页公开；
- 重大安全和数据红线不得豁免。

## 13.3 例外累计触发重审

同一条款：

- 连续出现 3 次例外；
- 或同时存在 3 个有效例外；
- 或累计延期超过 2 个迭代；

必须触发政策或架构重审。

## 13.4 例外补偿措施

可能包括：

- 增加监控；
- 限制流量；
- 关闭写入；
- 只读模式；
- 增加人工复核；
- 缩短发布窗口；
- 增加备份；
- 提高回滚优先级。

# 十四、风险分级与动态深审

## 14.1 风险评分

| 风险 | 权重 |
|---|---:|
| 数据不可逆 | 5 |
| 并发与锁 | 5 |
| 生命周期 | 5 |
| 安全与密钥 | 5 |
| 架构门禁 | 5 |
| 跨平台 | 4 |
| 外部服务 | 4 |
| migration 与回滚 | 4 |
| 性能与内存 | 3 |
| 普通 DTO | 1 |

## 14.2 深审触发

满足任一条件必须深审：

- 总分达到阈值；
- 修改公共合同；
- 修改数据 schema；
- 修改安全逻辑；
- 修改回滚机制；
- 修改 lint 或 CI；
- 修改验收脚本；
- 修改日志脱敏；
- 修改权限边界。

## 14.3 深审证据

深审不能只写“已看过”，必须输出：

- 风险清单；
- 反例；
- 故障注入；
- 并发分析；
- 数据恢复分析；
- 明确结论；
- 未解决项。

# 十五、故障注入制度

## 15.1 基础层

必须模拟：

- 配置校验失败；
- 回调异常；
- 容器启动中断；
- lazy 并发初始化；
- stop 超时；
- stop 异常；
- 日志目录不可写；
- psutil 失败；
- cache factory 失败；
- SyntaxError；
- 循环依赖；
- 缺失依赖；
- Windows 控制台事件。

## 15.2 基础设施层

必须模拟：

- 主模型超时；
- 备用模型失败；
- 熔断器半开竞争；
- DB locked；
- 连接池耗尽；
- migration 中断；
- WAL 降级；
- 模型文件损坏；
- embedding 加载失败；
- launcher 启动中断；
- shutdown 卡住。

## 15.3 有状态模块

必须模拟：

- 数据库写成功、索引写失败；
- 双写单边成功；
- 进程在事务边界崩溃；
- 文件部分写入；
- 快照损坏；
- 索引损坏；
- 重复消费；
- 死信队列溢出；
- 磁盘满。

## 15.4 验收内容

每个故障应验证：

- 是否保持一致；
- 是否正确降级；
- 是否有告警；
- 是否可定位；
- 是否继续服务；
- 是否能恢复；
- 是否会重复写；
- 是否能回滚。

# 十六、有状态变更防腐

## 16.1 事实真源

数据库或事件日志必须是事实真源。  
索引、缓存和快照不得成为唯一真源。

## 16.2 Expand–Migrate–Contract

执行：

```text
扩展兼容结构
→ 新旧代码都可读
→ 迁移历史数据
→ 双读校验
→ 新结构主用
→ 观察
→ 删除旧结构
```

## 16.3 双写规则

必须明确：

- 主源；
- 次源；
- 幂等键；
- 失败补偿；
- 重试；
- 对账；
- 灰度期读取；
- 回滚期读取。

## 16.4 migration 审计

记录：

```text
migration_id
schema_from
schema_to
commit_sha
started_at
finished_at
rows_scanned
rows_changed
checksum_before
checksum_after
status
error
rollback_id
```

## 16.5 回滚演练

不得只写回滚方案。必须执行：

```text
新版本写入
→ 产生新数据
→ 切回旧版本
→ 验证旧版可读
→ 验证无丢失
→ 验证无重复
→ 验证索引一致
```

# 十七、灰度与发布政策

## 17.1 灰度前条件

- 阶段已验收；
- 回滚已演练；
- 指标已配置；
- 告警已验证；
- 数据备份完成；
- 责任人在场；
- 发布窗口明确。

## 17.2 最低样本

示例：

```text
1% 灰度：
至少 1000 请求
至少 24 小时
关键场景全部覆盖
人工抽检不少于 100 条
无数据丢失
无安全事件
```

## 17.3 发布停止条件

任一发生立即停止：

- 数据丢失；
- 安全事件；
- 未处理异常增加；
- 5xx 明显高于旧链路；
- migration 不一致；
- 回滚能力失效；
- 指标不可用；
- 证据链中断。

## 17.4 回滚权限

值班发布负责人在红线触发时可直接回滚，无需等待长期审批。

# 十九、审计与随机抽查

## 19.1 定期审计

每个 Phase 结束后审计：

- 例外；
- skip/xfail；
- 测试删除；
- 状态变更；
- 高风险审批；
- 回滚记录；
- 生产异常；
- 文档漂移。

## 19.2 随机抽查

随机：

- 复跑已通过测试；
- 抽取已完成模块重新审查；
- 复验证据；
- 检查异常完美的指标；
- 检查长期无缺陷模块；
- 检查例外最多模块。

## 19.3 审计触发

以下情况自动触发专项审计：

- 阶段异常快速完成；
- 测试数量显著增加但缺陷率不变；
- 关键指标突然变好；
- 大量失败被改为 skip；
- 同一人长期包揽实现和验收；
- 例外连续续期；
- 文档频繁追溯修改；
- 生产事故与验收结论不一致。

# 二十、违规处理

## 20.1 流程后果

政策违规优先产生流程后果，而非仅口头提醒：

- 阻止合并；
- 阻止发布；
- 阶段状态回退；
- 强制重新验收；
- 扩大抽查；
- 暂停并行开发；
- 收紧权限；
- 关闭例外；
- 触发复盘。

## 20.2 严重违规

以下属于严重违规：

- 伪造测试结果；
- 删除失败记录；
- 隐瞒数据丢失；
- 隐瞒安全问题；
- 使用不匹配 commit 的报告；
- 未经批准修改验收标准；
- 将未运行项目标记为通过；
- 回滚失败后仍继续扩大流量。

## 20.3 违规与能力不足区分

政策应区分：

- 恶意规避；
- 疏忽；
- 工具不足；
- 政策不合理；
- 能力不足。

制度目标是恢复质量和责任链，而不是简单惩罚。

# 二十一、反馈与举报机制

建立独立风险渠道：

- 可匿名；
- 不经过原执行者过滤；
- 每个报告有编号；
- 处理状态可追踪；
- 重大问题自动升级；
- 关闭必须附证据；
- 报告人不因提出风险受损。

禁止用“已知悉”直接关闭。

# 二十二、政策自身的定期复审

防腐制度不能变成僵化制度。

每个大阶段复审：

1. 哪些条款例外最多；
2. 哪些条款无法自动验证；
3. 哪些指标诱发错误行为；
4. 哪些政策成本过高；
5. 哪些责任没有对应权限；
6. 哪些规则已经被技术替代；
7. 哪些红线发生过误报或漏报。

正式修改政策是允许的；私下绕过政策是不允许的。

# 二十六、最终完成定义

1. 状态不能由个人直接改成完成；

13. 历史失败记录不能被覆盖；
14. 随机审计真实执行；
15. 政策本身定期复审。

# 二十七、结论

防止工程政策腐化，不能只依赖参与者认真、自律或善意。

真正可靠的机制应当使：

- 模糊解释难以通过；
- 虚假完成难以生成；
- 违规路径被工具阻断；
- 例外无法永久存在；
- 历史无法被静默改写；
- 高风险决策具有明确责任；
- 每一个通过状态都能被重新验证；
- 每一次失败都成为改进政策的输入。

本项目最终应从：

```text
执行者说明自己已经完成
```

转变为：

```text
系统根据冻结政策、机器证据、独立审查和回滚演练，证明该阶段可以通过
```

最核心的一句话是：

> **不要让执行者证明自己做得对；要让制度要求他提交能够被第三方复现、能够被反证、无法通过口头解释替代的证据。**
