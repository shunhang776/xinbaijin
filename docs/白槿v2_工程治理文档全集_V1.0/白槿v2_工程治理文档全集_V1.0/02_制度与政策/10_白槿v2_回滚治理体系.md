# 白槿 v2 回滚治理体系

> 目的：将“可以恢复”从口头承诺变为每个任务都能验证的工程能力。

---

## 一、基本原则

- 每个任务开始前必须存在恢复点；
- 回滚方案必须与任务一起设计；
- 回滚必须实际演练；
- 回滚失败必须阻断验收；
- 数据变更不能只依靠 Git；
- 不可逆变更必须使用前向修复和备份恢复方案；
- 回滚报告必须绑定 commit、数据版本和工具版本。

---

## 二、风险分级

### L1：纯代码和文档

不涉及数据格式、数据库、密钥、权限。

回滚方式：Git commit/tag。

### L2：配置与依赖

涉及配置结构、锁文件、依赖升级。

回滚方式：Git + 环境重建验证。

### L3：数据库与持久化数据

涉及 schema、迁移、索引、数据转换。

回滚方式：Git + 数据备份 + 迁移回退或前向修复。

### L4：权限、安全和不可逆操作

涉及认证、授权、密钥轮换、删除数据、外部发布。

必须人工确认并进行隔离环境演练。

---

## 三、任务开始前

必须记录：

```text
baseline commit
baseline tag
依赖锁文件哈希
配置版本
数据库 schema 版本
数据备份位置
烟雾测试结果
```

推荐：

```bash
git add .
git commit -m "baseline before TASK-ID"
git tag baseline-TASK-ID
```

---

## 四、普通代码回滚演练

1. 保存候选改动；
2. 切换到 baseline；
3. 重建必要环境；
4. 运行最小烟雾测试；
5. 恢复候选改动；
6. 再次运行烟雾测试；
7. 比较结果；
8. 生成回滚报告。

必须覆盖未跟踪文件，不得只检查 tracked diff。

---

## 五、配置与依赖回滚

必须验证：

- 锁文件可恢复；
- 环境可以从锁文件重建；
- 旧配置仍可加载；
- 新旧配置迁移路径明确；
- 配置缺失时不会静默使用危险默认值。

---

## 六、数据库回滚

迁移前：

- 备份数据库；
- 记录 schema 版本；
- 记录关键表行数；
- 记录校验和；
- 在副本运行迁移。

迁移后：

- 验证 schema；
- 验证数据行数；
- 验证关键业务查询；
- 验证约束和索引；
- 验证旧版本是否还能恢复。

如果数据库不适合 downgrade，应制定前向修复：

```text
备份恢复
+
新迁移修正
+
数据校验
```

---

## 七、回滚报告

```markdown
# 回滚报告

- task_id:
- baseline_commit:
- candidate_commit:
- risk_level:
- rollback_started_at:
- rollback_finished_at:
- baseline_smoke_test:
- candidate_restore_test:
- database_backup:
- data_validation:
- result:
- unresolved_risks:
```

---

## 八、失败处理

以下情况状态必须为 `ROLLBACK_FAILED`：

- baseline 无法恢复；
- 恢复后无法启动；
- 未跟踪文件丢失；
- 依赖环境无法重建；
- 数据备份不可读取；
- 数据校验不一致；
- 恢复后的报告无法绑定正确版本。

`ROLLBACK_FAILED` 不得通过人工口头说明跳过。

---

## 九、定期恢复演练

- 每个高风险任务：必须演练；
- 每个 Phase：至少一次完整恢复；
- 每月：随机抽取一个历史任务；
- 备份策略变化：立即重新演练；
- 发生数据事故：重新验证整套机制。

---

## 十、最终原则

```text
没有实际恢复过
≠
可恢复

只有恢复演练成功
=
回滚能力已得到证明
```
