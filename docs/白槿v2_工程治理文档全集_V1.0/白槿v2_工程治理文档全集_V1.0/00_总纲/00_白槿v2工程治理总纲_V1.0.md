# 白槿 v2 工程治理总纲 V1.0

> 文件性质：白槿 v2 工程治理最高层级原则文件  
> 版本：V1.0  
> 日期：2026-06-18  
> 适用范围：白槿 v2 的需求、设计、开发、测试、审查、验收、发布、回滚和工程政策管理  
> 核心目的：终止“AI 快速堆代码—局部测试通过—架构持续腐化—最终整体推翻”的循环

---

## 一、总纲声明

白槿 v2 不再以“AI 已经写完代码”“测试数量增加”“功能暂时能运行”作为工程完成依据。

任何任务、修复批次或 Phase，只有在以下六项同时满足后，才允许被认定为完成：

```text
需求明确
证据完整
测试真实
审查独立
政策通过
回滚成功
```

白槿 v2 的正式工程链路为：

```text
需求
→ 开发
→ 测试
→ 审查
→ 验收
→ 回滚验证
→ ACCEPTED
```

AI 可以提出方案、生成代码和发现问题，但不得单独决定任务完成、Phase 完成或高风险变更放行。

---

## 二、V1 失败模式与 V2 风险

### 2.1 V1 的根本问题

V1 的失败不应只归因于代码质量差，更重要的原因是缺乏可执行的治理体系：

- 需求不断扩张；
- AI 同时充当架构师、开发者、测试者和审查者；
- 没有稳定的任务边界；
- 没有独立审查；
- 没有机器可执行的架构政策；
- 测试通过无法证明需求满足；
- 文档、代码、测试和真实行为不断漂移；
- 缺少可靠恢复点；
- 问题积累后只能整体推翻。

### 2.2 V2 正在出现的相似信号

- Phase 进度快于工程验证能力；
- 通用基础能力存在重复自研；
- “文件已创建”和“测试通过”被当作完成；
- AI 的解释被当作事实；
- 项目负责人无法独立核实代码；
- 审查依赖临时上传和对话；
- 治理系统尚未建立，业务代码继续增长。

因此，V2 必须先建设工程生产线，再继续扩大业务实现。

## 三、治理权力分离

白槿 v2 采用分权模式：

| 角色 | 主要职责 | 禁止事项 |
|---|---|---|
| 项目负责人 | 决定产品目标、风险容忍度、高风险放行 | 不以口头承诺替代证据 |
| Claude Code | 在批准范围内开发和修复 | 不得修改治理政策、受保护测试和最终验收状态 |
| 开源确定性工具 | 静态检查、类型、架构、测试、安全 | 不对业务语义作最终判断 |
| Codex CLI | 只读独立代码审查 | 不直接修改候选代码，不单独决定放行 |
| OPA/Conftest | 根据结构化证据执行政策 | 不生成业务代码 |
| ChatGPT/真人审查者 | 复核复杂设计与高风险变更 | 不替代自动化基础证据 |

核心原则：

```text
开发权
≠
审查权
≠
政策修改权
≠
最终放行权
```

## 四、可信边界

建议将业务仓库与治理仓库隔离：

```text
D:\白槿v2\
D:\白槿治理\
```

### 业务仓库

包含：

- 业务代码；
- 普通测试；
- 任务文件；
- 项目配置；
- 本次审查产物；
- Git 历史。

Claude 可以在任务允许范围内读写。

### 治理仓库

包含：

- OPA 政策；
- 受保护测试；
- 审查结果 Schema；
- 投毒样例；
- 结果适配器；
- 最终报告模板；
- 状态转换规则；
- 回滚验证入口。

Claude 原则上只能读取和执行，不能直接修改。

## 五、开源优先原则

代码审查系统的大部分核心能力必须采用成熟开源技术。

推荐基础栈：

```text
Git
+ pre-commit
+ Nox
+ Ruff
+ mypy
+ Import Linter
+ pytest
+ Hypothesis
+ Gitleaks
+ pip-audit
+ Semgrep / OpenGrep
+ OPA / Conftest
+ Codex CLI
```

### 不应自行开发

- Git diff 与版本历史；
- Hook 管理框架；
- 测试执行器；
- Python formatter 和 linter；
- 类型分析器；
- 通用 import 依赖图；
- 通用循环依赖算法；
- 密钥扫描器；
- 漏洞数据库；
- 通用安全规则引擎；
- 通用政策语言；
- 变异测试框架；
- 大型质量平台。

### 可以自研

- 白槿专属架构合同；
- P0/P1 定义；
- 任务和验收模板；
- 工具输出适配器；
- Codex 结构化审查提示；
- OPA 白槿政策；
- 负责人中文报告；
- Claude Hook 编排；
- 审查包打包；
- 白槿专属受保护测试。

目标比例：

```text
85%～95% 成熟开源组件
5%～15% 白槿专属适配、政策和报告
```

## 六、任务状态机

正式状态：

```text
DRAFT
→ READY
→ IMPLEMENTING
→ TESTING
→ REVIEWING
→ ACCEPTING
→ ACCEPTED
```

失败状态：

```text
BLOCKED
TEST_FAILED
REVIEW_FAILED
POLICY_FAILED
ROLLBACK_FAILED
NEEDS_HUMAN_REVIEW
```

禁止使用“基本完成”“大致完成”“已经实现”等模糊词作为正式状态。

只有治理程序可以将任务设置为 `ACCEPTED`。

---

## 七、需求治理

每个任务必须包含：

```text
task.md
acceptance.yaml
risk.yaml
status.yaml
```

任务必须说明：

- 目标；
- 非目标；
- 允许修改范围；
- 禁止修改范围；
- 可验证验收条件；
- 必须覆盖的失败路径；
- 风险等级；
- 数据影响；
- 回滚要求；
- 是否需要人工确认。

需求未冻结不得进入开发。

任务开始后，开发者不得自行修改验收标准。需求变化必须通过独立变更记录。

---

## 八、开发治理

每次任务开始前必须建立 Git 基线：

```bash
git add .
git commit -m "baseline before TASK-ID"
git tag baseline-TASK-ID
```

每个任务应保持小批次：

- 核心文件建议不超过 5～8 个；
- 核心代码改动建议不超过约 500 行；
- 不跨多个 Phase；
- 不同时修改业务、数据库和治理政策；
- 不允许“顺便重构”。

开发结束后必须生成：

```text
working-tree-status.txt
changed-files.txt
diff-stat.txt
patch.diff
current-commit.txt
changed/
```

其中 `changed/` 保存修改后的完整文件。`git diff` 只是审查证据的一部分，不是完整审查包。

## 九、测试治理

Nox 作为统一执行入口，组织：

- Ruff；
- mypy；
- Import Linter；
- pytest；
- Hypothesis；
- Gitleaks；
- pip-audit；
- Semgrep/OpenGrep。

测试按层次组织：

```text
tests/
├── unit/
├── contracts/
├── integration/
├── acceptance/
├── fault_injection/
└── policy/
```

测试通过必须满足：

- 所有 required checks 实际运行；
- 所有报告存在；
- 报告绑定当前 commit；
- 失败数为 0；
- 关键测试没有被 skip；
- 受保护测试没有被删除；
- 测试数量异常下降会报警；
- 工具异常时默认失败。

---

## 十、独立审查

Codex CLI 作为独立、只读审查者，输入至少包括：

- 任务目标；
- 验收标准；
- 风险说明；
- Git 变更；
- 修改后的完整文件；
- 静态检查报告；
- 测试报告；
- 安全报告；
- 架构合同结果。

Codex 输出必须是符合 Schema 的结构化 JSON，包括：

- `safe_to_accept`；
- P0、P1、P2；
- 缺失测试；
- 范围外修改；
- 政策违规；
- 是否需要人工确认。

自然语言散文不得作为自动验收输入。

---

## 十一、政策验收

所有结果统一转换为：

```text
review-input.json
```

OPA/Conftest 根据正式政策决定：

- 通过；
- 拒绝；
- 要求人工确认。

以下情况必须拒绝：

- 证据不完整；
- commit 不匹配；
- 范围外修改；
- 测试失败；
- 架构合同失败；
- 密钥泄漏；
- P0/P1 未清零；
- Codex 拒绝；
- 恢复点缺失；
- 回滚演练失败；
- 政策引擎异常。

以下情况必须人工确认：

- 数据库迁移；
- 用户数据删除；
- 身份认证；
- 权限；
- 密钥；
- 治理政策；
- 发布配置；
- 不可逆数据格式变化。

---

## 十二、回滚治理

回滚必须实际验证，而不是只写命令。

普通代码任务必须：

```text
保存候选改动
→ 回退至 baseline
→ 运行烟雾测试
→ 恢复候选改动
→ 再次运行烟雾测试
→ 保存回滚报告
```

数据库任务必须额外包括：

- 迁移前备份；
- schema 版本；
- 数据数量与校验和；
- 副本演练；
- 回滚脚本或前向修复方案；
- 恢复时间记录。

---

## 十三、投毒测试

审查系统必须先在已知答案样例上验证。

至少包括：

```text
good_case
syntax_error
circular_import
failing_test
deleted_protected_test
skipped_core_test
always_true_assert
secret_leak
vulnerable_dependency
p0_open
p1_open
codex_rejected
missing_report
commit_mismatch
governance_modified
rollback_failed
```

必须满足：

```text
好样例能通过
坏样例能拦截
工具异常默认失败
证据缺失默认失败
政策修改会报警
回滚失败禁止验收
```

---

## 十四、Phase 完成政策

Phase 不因“文件写完”或“全部测试绿灯”而完成。

Phase 完成必须满足：

- 所有纳入范围的任务均为 `ACCEPTED`；
- 架构合同通过；
- 验收测试通过；
- P0 = 0；
- P1 = 0；
- Codex 独立审查通过；
- OPA 最终政策通过；
- 回滚演练通过；
- 数据迁移已验证；
- 例外已登记且未过期；
- 治理规则没有未经批准的修改。

任何一项不满足，禁止进入下一 Phase。

---

## 十五、例外管理

禁止通过永久 ignore、全局关闭规则、删除测试或降低阈值来制造绿灯。

所有例外必须：

- 有唯一编号；
- 有业务理由；
- 有影响范围；
- 有责任人；
- 有补偿控制；
- 有到期时间；
- 到期后自动失败；
- 不得自动续期；
- 高风险例外必须人工批准。

---

## 十六、负责人报告

项目负责人只需要阅读统一报告：

```text
final-report.md
```

必须显示：

- 任务目标；
- 修改范围；
- 范围外修改；
- 数据和安全影响；
- 各工具结果；
- Codex P0/P1；
- OPA 拒绝项；
- 人工确认项；
- 回滚结果；
- 最终状态。

工具原始报告保留供追溯，但不要求负责人逐项阅读。

---

## 十七、治理系统启用标准

治理系统在满足以下条件后，才可以接管 Phase 1：

- 一个好样例稳定通过；
- 所有投毒样例稳定被拒绝；
- 工具崩溃默认拒绝；
- Claude 无法修改治理政策；
- 报告绑定当前 commit；
- Codex 拒绝时 OPA 一定拒绝；
- OPA 政策拥有正反测试；
- 完成两次真实回滚；
- 完成三个低风险真实任务；
- 负责人能够直接理解最终报告。

启用状态定义为：

```text
PROVISIONALLY_TRUSTED
```

即“暂时可信”，而不是绝对正确。

---

## 十八、第一阶段执行顺序

```text
1. 暂停 Phase 1 开发
2. 建立业务仓库和治理仓库
3. 建立任务模板和状态机
4. 建立 Git 基线与证据收集
5. 配置 Nox、Ruff、pytest、Import Linter
6. 配置 OPA/Conftest
7. 建立好样例和投毒样例
8. 接入 Codex 只读审查
9. 生成统一负责人报告
10. 完成真实回滚演练
11. 接入 Claude Stop Hook
12. 完成三个低风险真实任务
13. 再开始 Phase 1 分批整改
```

---

## 十九、最高原则

白槿 v2 的工程事实不再由 AI 的语言决定，而由证据链决定：

```text
需求定义做什么
Git记录实际做了什么
开源工具验证确定性规则
Codex发现深层设计问题
OPA执行正式政策
回滚限制失败后果
```

只有需求、开发、测试、审查、验收和回滚形成闭环，白槿 v2 才真正走上与 v1 不同的道路。
