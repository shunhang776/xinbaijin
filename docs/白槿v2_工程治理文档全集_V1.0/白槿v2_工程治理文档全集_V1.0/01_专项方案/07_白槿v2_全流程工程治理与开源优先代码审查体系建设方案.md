# 白槿 v2 全流程工程治理与开源优先代码审查体系建设方案

> 文档类型：工程治理、代码审查、阶段验收与回滚体系总方案  
> 适用项目：白槿 v2  
> 适用场景：Claude Code 负责开发、Codex CLI 负责独立审查、项目负责人进行最终决策  
> 核心目标：建立一条可验证、可追踪、可阻断、可回滚的工程治理链路，防止白槿 v2 重走 v1“AI 快速堆代码、后期失控、最终推翻重写”的老路  
> 技术原则：**代码审查系统大规模采用成熟开源技术，项目自研部分仅保留白槿专属政策、工具适配、任务状态和负责人报告**

---

# 一、背景与问题定义

白槿 v1 的主要失败风险并不只是“代码写得不好”，而是整个开发过程缺少稳定的治理链路。

典型失控过程如下：

```text
提出需求
↓
让 AI 写代码
↓
功能暂时能运行
↓
继续追加功能
↓
AI 不断修改已有代码
↓
架构边界逐渐模糊
↓
测试无法证明真实正确性
↓
项目负责人无法判断是否完成
↓
代码越来越难理解和修改
↓
最终推翻重写
```

白槿 v2 当前已经出现与 v1 相似的危险信号：

- 开发速度高于验证速度；
- Phase 不断推进，但验收体系尚未建立；
- Claude 同时承担设计、开发、自测和解释；
- “测试通过”被误认为“阶段完成”；
- 项目负责人无法直接确认 AI 是否真的完成任务；
- 架构、合同、测试和文档之间存在漂移；
- 通用基础检查存在自研倾向；
- 缺少独立审查、正式验收和实际回滚演练；
- 代码审查依赖临时上传和人工交流，无法规模化。

因此，白槿 v2 在继续推进 Phase 1 之前，应优先建立完整治理链路：

```text
需求
→ 开发
→ 测试
→ 审查
→ 验收
→ 回滚
```

这条链路不是辅助工具，而是白槿 v2 后续所有开发工作的基础设施。

# 二、总体目标

本体系要解决六个核心问题。

## 2.1 需求是否明确

必须明确：

- 这次任务要解决什么；
- 什么不属于本次任务；
- 哪些文件允许修改；
- 哪些文件禁止修改；
- 如何判断任务完成；
- 哪些风险需要人工确认。

## 2.2 AI 实际修改了什么

不能依赖 Claude 的口头总结。

必须由 Git 记录：

- 修改文件；
- 新增文件；
- 删除文件；
- 具体 diff；
- 修改后的完整文件；
- 当前 commit；
- 修改前基线。

## 2.3 代码是否通过确定性验证

不能只依赖 AI 自测。

必须使用成熟开源工具验证：

- 格式；
- 静态错误；
- 类型；
- 架构依赖；
- 单元测试；
- 合同测试；
- 集成测试；
- 安全问题；
- 密钥泄漏；
- 依赖漏洞。

## 2.4 是否存在机器工具难以发现的问题

由独立 AI 审查：

- 设计偏离；
- 生命周期问题；
- 并发问题；
- 测试不足；
- 回滚不完整；
- 隐含副作用；
- 跨模块影响；
- 文档与代码不一致。

## 2.5 谁决定任务是否完成

不能由 Claude 自己决定。

应由：

```text
结构化证据
+
OPA / Conftest 政策
+
Codex 审查结果
```

共同决定。

## 2.6 失败后是否可以恢复

每次任务都必须：

- 有修改前恢复点；
- 有回滚方案；
- 实际执行回滚演练；
- 确认回滚后系统仍可运行；
- 涉及数据时验证数据完整性。

# 三、总体治理链路

完整链路如下：

```text
需求冻结
    ↓
建立 Git 恢复点
    ↓
Claude Code 开发
    ↓
收集真实变更证据
    ↓
Nox 编排确定性检查
    ├── Ruff
    ├── mypy
    ├── Import Linter
    ├── pytest
    ├── Hypothesis
    ├── Gitleaks
    ├── pip-audit
    └── Semgrep / OpenGrep
    ↓
生成统一 review-input.json
    ↓
OPA + Conftest 初次政策裁决
    ↓
Codex CLI 只读独立审查
    ↓
生成 codex-review.json
    ↓
OPA + Conftest 最终裁决
    ↓
生成 final-report.md
    ↓
实际回滚验证
    ↓
任务状态变为 ACCEPTED
```

只要任意环节失败：

```text
停止进入下一阶段
→ 记录失败原因
→ 修复后重新执行全部相关检查
```

# 四、核心原则

## 4.1 成熟开源优先

审查系统的核心功能不从零自研。

成熟开源组件承担：

- Git 变更追踪；
- Hook 管理；
- 测试编排；
- 静态分析；
- 类型检查；
- 架构检查；
- 测试执行；
- 属性测试；
- 安全扫描；
- 密钥扫描；
- 漏洞扫描；
- 政策执行；
- 结果聚合；
- 变异测试；
- 可视化分析。

白槿只自研：

- 白槿专属政策；
- 工具结果适配；
- 任务状态；
- Codex 结构化输出 Schema；
- 负责人中文报告；
- Claude Hook 编排；
- 审查包生成。

目标比例：

```text
85%～95% 成熟开源组件
+
5%～15% 白槿专属适配、政策和报告
```

## 4.2 确定性工具优先于 AI

执行顺序必须是：

```text
开源确定性工具
↓
政策引擎
↓
Codex 深度审查
↓
政策引擎最终裁决
```

Codex 不替代：

- Ruff；
- mypy；
- Import Linter；
- pytest；
- Gitleaks；
- pip-audit；
- Semgrep；
- OPA。

## 4.3 写代码者不能修改验收规则

Claude 负责业务代码。

Claude 不得直接修改：

- OPA 政策；
- 受保护测试；
- Codex 审查 Schema；
- 验收结果；
- Phase 完成规则；
- 回滚政策；
- P0/P1 定义。

如果治理规则确实需要修改，必须建立独立治理任务，并由项目负责人人工确认。

## 4.4 缺少证据默认失败

必须采用 fail closed 原则：

```text
报告缺失
工具异常
结果无法解析
commit 不匹配
Schema 校验失败
Codex 输出不完整
OPA 解析失败
```

全部视为失败。

不能使用：

```text
没有发现问题
=
通过
```

而应使用：

```text
有完整证据证明通过
=
通过
```

## 4.5 小批次开发

每个任务建议：

- 修改不超过 5～8 个核心文件；
- 核心代码改动不超过约 500 行；
- 不同时修改业务代码、数据库和治理规则；
- 不跨多个 Phase；
- 不在修 bug 时顺便大规模重构；
- 自动修复循环最多两轮。

# 六、统一任务状态机

禁止使用：

```text
基本完成
差不多完成
已实现
测试通过
```

代替正式任务状态。

每个任务必须处于以下状态之一：

```text
DRAFT
→ READY
→ IMPLEMENTING
→ TESTING
→ REVIEWING
→ ACCEPTING
→ ACCEPTED
```

失败状态：

```text
BLOCKED
TEST_FAILED
REVIEW_FAILED
POLICY_FAILED
ROLLBACK_FAILED
NEEDS_HUMAN_REVIEW
```

状态含义：

| 状态 | 含义 |
|---|---|
| DRAFT | 需求尚未冻结 |
| READY | 需求和验收标准已准备 |
| IMPLEMENTING | Claude 正在开发 |
| TESTING | 正在运行确定性检查 |
| REVIEWING | Codex 正在独立审查 |
| ACCEPTING | OPA 正在最终裁决 |
| ACCEPTED | 所有门禁和回滚均通过 |
| BLOCKED | 任务被阻断 |
| TEST_FAILED | 测试或静态检查失败 |
| REVIEW_FAILED | Codex 审查拒绝 |
| POLICY_FAILED | OPA 政策拒绝 |
| ROLLBACK_FAILED | 回滚演练失败 |
| NEEDS_HUMAN_REVIEW | 高风险或自动修复超过限制 |

只有门禁程序可以将状态设置为：

```text
ACCEPTED
```

Claude 和 Codex 均不能直接修改最终状态。

# 七、第一环：需求治理

# 7.1 任务目录

每个任务创建独立目录：

```text
tasks/
└── PHASE1-R1/
    ├── task.md
    ├── acceptance.yaml
    ├── risk.yaml
    └── status.yaml
```

## 7.2 task.md

示例：

```markdown
# PHASE1-R1

## 目标

修复 core 公共导出和循环依赖检查。

## 允许修改

- core/__init__.py
- scripts/ops/lint_imports.py
- tests/contracts/**

## 禁止修改

- 数据库
- Phase 2 代码
- 治理规则
- 公共配置格式
- 密钥和权限相关文件

## 必须实现

1. 规定的公共符号可以正确导入；
2. 两模块直接循环能够被发现；
3. 三模块间接循环能够被发现；
4. SyntaxError 必须导致检查失败；
5. 原有受保护测试不得减少；
6. 检查器异常时必须返回失败。

## 非目标

- 不重构整个 core；
- 不修改依赖注入框架；
- 不修改数据库；
- 不升级 Phase 2 代码。
```

## 7.3 acceptance.yaml

```yaml
task_id: PHASE1-R1

allowed_paths:
  - core/__init__.py
  - scripts/ops/lint_imports.py
  - tests/contracts/**

required_checks:
  - ruff
  - mypy
  - import_linter
  - pytest
  - gitleaks
  - codex_review

limits:
  max_changed_files: 6
  max_changed_lines: 500
  max_p0: 0
  max_p1: 0
  max_auto_repair_cycles: 2

forbidden_changes:
  database: true
  governance: true
  secrets: true
  authentication: true
```

## 7.4 risk.yaml

```yaml
task_id: PHASE1-R1

risk_level: medium

data_change: false
database_migration: false
security_change: false
governance_change: false
public_api_change: true

rollback_required: true
human_review_required: false
```

## 7.5 需求阶段通过条件

需求必须满足：

- 目标可验证；
- 允许修改范围明确；
- 禁止修改范围明确；
- 必须实现项可测试；
- 至少定义一个失败场景；
- 风险等级明确；
- 回滚要求明确；
- 高风险变更是否需要人工确认已明确。

需求未冻结，不允许进入开发状态。

# 八、第二环：开发治理

# 8.1 建立基线恢复点

任务开始前：

```bash
git status
git add .
git commit -m "baseline before PHASE1-R1"
git tag baseline-PHASE1-R1
```

记录：

```text
baseline commit
baseline tag
任务开始时间
当前依赖锁文件
当前测试结果
```

## 8.2 Claude 开发权限

Claude 可以：

- 修改允许范围内的业务代码；
- 增加普通测试；
- 运行 Nox；
- 阅读治理报告；
- 根据明确问题修复代码。

Claude 不可以：

- 修改 `acceptance.yaml`；
- 修改 OPA 政策；
- 删除受保护测试；
- 将失败测试改为 skip；
- 使用 `or True` 等永真断言；
- 通过扩大 try/except 隐藏错误；
- 修改治理系统结果；
- 自行设置任务状态为 ACCEPTED。

## 8.3 真实变更证据

任务开发完成后运行：

```bash
git status --porcelain
git diff --name-status HEAD
git diff --stat HEAD
git diff --binary HEAD
git rev-parse HEAD
```

生成：

```text
artifacts/current/
├── working-tree-status.txt
├── changed-files.txt
├── diff-stat.txt
├── patch.diff
├── current-commit.txt
└── changed/
```

`changed/` 中复制所有修改后的完整文件。

完整文件用于发现：

- 文件级上下文问题；
- 现有导入关系；
- 非修改区域和新增代码的组合错误；
- 文件内不变量；
- 间接依赖；
- 局部 diff 无法显示的问题。

# 九、第三环：测试治理

测试阶段必须优先使用成熟开源项目。

# 9.1 Nox：统一执行入口

Nox 负责统一编排：

```text
lint
types
architecture
unit tests
contract tests
integration tests
security
acceptance
```

以后不维护大量独立的：

```text
run_tests.py
run_lint.py
run_security.py
run_all_checks.py
```

建议会话：

```python
import nox


@nox.session
def lint(session):
    session.install("ruff")
    session.run("ruff", "format", "--check", ".")
    session.run("ruff", "check", ".")


@nox.session
def types(session):
    session.install("mypy")
    session.run("mypy", "core", "infra", "services")


@nox.session
def architecture(session):
    session.install("import-linter")
    session.run("lint-imports")


@nox.session
def tests(session):
    session.install(".")
    session.install("pytest", "hypothesis")
    session.run(
        "pytest",
        "--junitxml=artifacts/current/pytest.xml",
    )


@nox.session
def secrets(session):
    session.run("gitleaks", "detect", "--source", ".", external=True)
```

统一执行：

```bash
nox
```

# 9.2 Ruff

负责：

- Python 格式；
- import 顺序；
- 未使用变量；
- 未使用 import；
- 常见代码错误；
- 一部分复杂度规则；
- 一部分安全规则；
- 现代 Python 语法。

正式门禁使用：

```bash
ruff format --check .
ruff check .
```

自动修复仅允许在开发阶段使用：

```bash
ruff format .
ruff check --fix .
```

# 9.3 mypy

负责：

- 函数参数；
- 返回值；
- Optional；
- Protocol；
- DTO；
- Result；
- Repository；
- async 接口；
- 公共合同类型一致性。

采用渐进式严格策略，不要求第一天全项目严格模式。

# 9.4 Import Linter

负责：

- 层级依赖；
- 禁止依赖；
- 独立模块；
- protected modules；
- 循环依赖；
- core 与 infra 边界；
- domain 与 app 边界。

使用 Import Linter 取代通用自研依赖图和循环依赖分析器。

# 9.5 pytest

测试目录：

```text
tests/
├── unit/
├── contracts/
├── integration/
├── acceptance/
├── fault_injection/
└── policy/
```

职责：

| 目录 | 作用 |
|---|---|
| unit | 函数和类 |
| contracts | 公共导入、DTO、Protocol、异常合同 |
| integration | 多模块真实协作 |
| acceptance | 当前任务完成标准 |
| fault_injection | 启动失败、回滚、超时、DB locked |
| policy | 治理系统自身规则 |

必须生成 JUnit XML：

```bash
pytest --junitxml=artifacts/current/pytest.xml
```

# 9.6 Hypothesis

用于：

- 时间边界；
- Unicode；
- 配置解析；
- DTO 不变量；
- Result 状态；
- 序列化往返；
- 缓存状态；
- 状态机；
- 极端输入。

# 9.7 Gitleaks

用于扫描：

- API Key；
- Token；
- 密码；
- 私钥；
- 云凭证；
- `.env`；
- Git 历史中的秘密。

检测到密钥泄漏时必须阻断。

# 9.8 pip-audit

用于扫描 Python 依赖中的已知漏洞。

高严重性且与项目实际调用路径相关的漏洞必须阻断。

# 9.9 Semgrep CE 或 OpenGrep

用于：

- `eval`、`exec`；
- shell 注入；
- 不安全反序列化；
- 裸异常；
- 危险文件删除；
- 日志输出 SecretStr；
- 绕过统一安全包装；
- 白槿专属危险模式。

项目只维护少量白槿专属规则，不自行开发规则引擎。

# 9.10 reviewdog

第二阶段接入，用于：

- 汇总多个工具结果；
- 映射到文件和行；
- 聚焦当前 diff 新增问题；
- 减少历史问题噪声。

# 9.11 mutmut

第三阶段通过 WSL 接入，用于验证测试是否真的能够发现代码错误。

不要求每次小改动都运行，可以：

- 每周运行；
- 每个 Phase 验收前运行；
- 核心模块重大修改后运行。

# 十、测试阶段门禁

测试通过必须同时满足：

```text
所有 required_checks 已实际运行
所有工具退出码符合要求
JUnit XML 存在
测试失败数为 0
关键测试未被 skip
受保护测试未删除
报告对应当前 commit
工具版本已记录
```

以下情况一律失败：

```text
报告缺失
报告为空

工具崩溃
关键测试被跳过
受保护测试被删除
测试数量异常下降
commit 与报告不匹配
```

# 十一、第四环：独立代码审查

# 11.1 角色分离

```text
Claude Code
=
开发者

Codex CLI
=
独立审查者

开源检查工具
=
确定性验证者

OPA / Conftest
=
政策裁决者

项目负责人
=
高风险最终批准者
```

Claude 不能审查并批准自己的工作。

# 11.2 Codex 审查输入

至少包括：

```text

acceptance.yaml
risk.yaml
changed-files.txt
patch.diff
修改后的完整文件
pytest.xml
Ruff 结果
mypy 结果
Import Linter 结果
Gitleaks 结果
Semgrep 结果
依赖漏洞结果
```

# 11.3 Codex 审查重点

Codex 主要审查：

- 是否真正满足任务目标；
- 是否存在范围外修改；
- 是否破坏公共合同；
- 是否存在生命周期缺陷；
- 是否存在并发窗口；
- 是否遗漏调用方；
- 是否通过删测试、skip、永真断言获得绿灯；
- 是否缺少异常路径；
- 回滚是否完整；
- 数据一致性是否安全；
- 文档是否与代码一致；
- 测试是否足以证明设计；
- 是否产生新的高风险技术债。

# 11.4 只读权限

Codex 审查阶段只能读取，不得直接修改代码。

Codex 如果发现问题，只输出结构化报告。

# 11.5 结构化输出


```text

```

# 11.6 修复循环

```text

→ Claude 读取明确问题
→ Claude 修复
→ 重新运行全部检查
→ 重新生成证据
→ Codex 再审查
```

最多两轮。

两轮后仍失败：

```text
状态 = NEEDS_HUMAN_REVIEW
```

禁止无限自动修复。

# 十三、第六环：回滚治理

回滚不是文档中写一句：

```text
可以 git reset
```

而必须实际执行。

# 13.1 普通代码任务

流程：

```text
保存候选改动
→ 回到 baseline tag
→ 运行最小烟雾测试
→ 恢复候选改动
→ 再次运行烟雾测试
→ 记录结果
```

必须验证：

- 能回到修改前状态；
- 修改前系统仍可启动；
- 恢复候选版本后结果一致；
- 未跟踪文件没有遗漏；
- 配置和依赖锁文件能够恢复。

# 13.2 数据库任务

必须额外具备：

- 迁移前数据库备份；
- schema 版本；
- 数据数量统计；
- 校验和；
- 迁移后数据验证；
- 回滚脚本或前向修复方案；
- 在数据库副本上演练；
- 数据恢复时间记录。

# 13.3 必须人工确认的高风险任务

以下内容不得完全自动验收：

```text
数据库迁移
删除用户数据
身份认证
权限系统
密钥
治理政策
发布配置
备份与恢复逻辑
用户隐私数据
不可逆格式转换
```

统一状态：

```text
NEEDS_HUMAN_REVIEW
```

# 十八、Phase 完成政策

Phase 不因“代码写完”而完成。

Phase 完成必须满足：

```text
所有任务均为 ACCEPTED
所有架构合同通过
所有验收测试通过
P0 = 0
P1 = 0
Codex 独立审查通过
OPA 最终政策通过
回滚演练通过
数据迁移已验证
风险和例外已记录
治理规则没有未经批准的修改
```

任何一项不满足：

```text
Phase 不得完成
不得进入下一 Phase
```

Phase 状态只能来源于所有任务状态的聚合，不允许手工填写“完成”。

# 十九、例外机制

某些问题可能暂时无法立即修复，但不能通过修改规则隐藏。

例外必须记录：

```yaml
exception_id: EX-2026-001
rule: MYPY-STRICT-001
reason: 历史模块暂未完成类型迁移
owner: project-owner
created_at: 2026-06-18
expires_at: 2026-07-01
affected_paths:
  - legacy/module.py
compensating_control:
  - 禁止修改该模块公共接口
  - 每次变更必须人工审查
```

例外必须：

- 有编号；
- 有原因；
- 有责任人；
- 有影响范围；
- 有补偿措施；
- 有到期时间；
- 到期后自动失败。

禁止：

```text
永久 ignore
全局关闭规则
大范围 noqa
为了通过而降低阈值
```

# 二十四、关键风险

## 24.1 工具过多

工具越多不等于越安全。

可能导致：

- 配置冲突；
- 运行时间过长；
- 重复报告；
- 大量误报；
- Claude 随意添加 ignore；
- 项目负责人无法理解结果。

因此必须逐步增加。

## 24.2 治理系统被 Claude 修改

如果 Claude 可以修改政策和受保护测试，门禁失去意义。

必须隔离权限。

## 24.3 Codex 和 Claude 同源偏差

两个 AI 仍可能犯相似错误。

因此确定性工具和 OPA 必须先于 AI 审查。

## 24.4 只看通过数量

“312 passed”不能证明任务完成。

必须同时验证：

- 测试是否覆盖目标；
- 受保护测试是否还在；
- 是否存在永真断言；
- 是否缺少失败路径；
- 是否修改了验收标准。

## 24.5 自动修复无限循环

自动修复最多两轮。

继续失败必须交给人工或重新拆解任务。

## 24.6 先建复杂平台

一开始部署 MegaLinter、SonarQube、远程 CI 和复杂 Web 面板，容易把治理建设变成新的大型项目。

第一阶段必须先跑通最小闭环。

---

# 二十五、最终验收标准

治理链路可以接管白槿 v2，必须满足：

```text
[ ] 好样例稳定通过
[ ] 所有投毒样例稳定失败
[ ] 工具异常时默认拒绝
[ ] Claude 无法修改治理政策
[ ] 报告绑定当前 Git commit
[ ] 缺少证据时默认拒绝
[ ] Codex 拒绝时 OPA 必须拒绝
[ ] OPA 政策有完整测试
[ ] 已成功完成两次真实回滚
[ ] 已完成三个低风险真实任务
[ ] 最终报告能够由项目负责人直接理解
[ ] 数据库、密钥、权限和治理变更必须人工确认
```

达到后，系统只能被定义为：

```text
PROVISIONALLY_TRUSTED
```

即暂时可信，而不是绝对正确。

# 二十六、最终结论

白槿 v2 需要停止依赖：

```text
AI 说完成
=
任务完成
```

新的工程事实应当是：

```text
需求定义做什么
Git记录实际做了什么
开源工具证明代码是否满足确定性规则
Codex发现规则之外的深层问题
OPA决定是否符合正式政策
回滚保证失败后可以恢复
```

完整治理链路是：

```text
需求
→ 开发
→ 测试
→ 审查
→ 验收
→ 回滚
```

完整审查技术栈是：

```text
Git
+
pre-commit
+
Nox
+
Ruff
+
mypy
+
Import Linter
+
pytest
+
Hypothesis
+
Gitleaks
+
pip-audit
+
Semgrep / OpenGrep
+
OPA / Conftest
+
Codex CLI
```

其中：

```text
Claude Code
=
受约束的开发者

Codex CLI
=
只读独立审查者

开源工具
=
确定性验证基础

OPA / Conftest
=
正式政策裁决者

项目负责人
=
高风险最终批准者
```

只有在：

```text
需求明确
证据完整
测试真实
审查独立
政策通过
回滚成功
```

六项同时满足时，任务才可以进入：

```text
ACCEPTED
```

这套体系真正建立并经过投毒验证后，白槿 v2 才会与 v1 的开发模式彻底分离，不再依赖 AI 自觉，不再依赖口头汇报，也不再通过不断推翻重写来解决工程失控问题。
