# 白槿 v2 执行方案实际缺陷与系统性补救方案

> 文档类型：执行纠偏、质量治理与落地改造方案  
> 适用范围：白槿 v2 全阶段重构计划  
> 适用对象：项目负责人、代码实现者、审查者、验收者、测试维护者  
> 当前背景：方案总体架构方向正确，但在实际执行中暴露出假完成、验收失真、测试与设计脱节、文档漂移、横向铺开过快、风险审查不足、灰度指标含糊及有状态回滚不完整等问题  
> 核心目标：在不推翻原有架构蓝图的前提下，建立一套可验证、可回滚、可追踪、可持续执行的工程治理机制

---

# 一、问题背景

白槿 v2 的重构方案在架构方向上具有较强的工程意识。它按照基础核心层、基础设施层、索引与存储层、记忆层、人格与状态层、服务与领域层、插件与提示词层、应用与运维层逐步推进，并包含以下较成熟的设计思想：

- 配置统一管理；
- 公共 DTO 和 Protocol 收口；
- 分层异常体系；
- 依赖注入容器；
- 生命周期编排；
- 优雅停止；
- 结构化日志；
- 指标采集；
- 灰度和影子对比；
- 熔断、重试、降级；
- 数据迁移；
- 脚手架和模板；
- lint 架构规则；
- 旧代码转发层；
- 分阶段回滚。

这些方向本身没有根本性错误。

实际问题主要出现在“执行方式”和“验收方式”上。Phase 1 已经出现了典型现象：

1. 文件已生成，但公共导出合同没有真正满足；
2. 现有测试全部通过，但设计指标没有全部实现；
3. 进度表写“完成”，实际合同验证仍然失败；
4. 方案要求真实循环依赖检测，但 lint 只能检测自导入；
5. 方案要求 Protocol 实现验证，但容器没有真正执行；
6. 方案要求 Windows 控制台关闭事件，但实现缺失；
7. requirements 能在当前环境运行，不代表干净环境可安装；
8. 测试数量很多，但部分测试断言并不能证明目标功能；
9. 文档描述与代码真实内容发生明显漂移；
10. 后续阶段已开始构建，但基础合同仍不稳定。

因此，当前需要解决的并不是单个文件的 bug，而是三层问题：

```text
代码实现缺陷
+
验收机制缺陷
+
执行管理缺陷
```

仅修代码而不改变执行和验收机制，后续阶段仍会重复出现同类问题。

# 二、总体判断

这份方案应继续保留，但必须改变执行方式。

| 维度 | 判断 |
|---|---|
| 架构蓝图 | 可继续使用 |
| 模块分层 | 基本合理 |
| 风险意识 | 较强 |
| 阶段顺序 | 基本合理，但缺少早期纵向验证 |
| 自动化治理思路 | 正确，但实际规则实现不足 |
| 测试数量 | 较多，但合同覆盖不足 |
| 进度可信度 | 当前不足 |
| 回滚完整性 | 无状态部分较好，有状态部分不足 |
| 实际执行效率 | 横向铺开过快，返工风险高 |
| 是否推倒重来 | 不需要 |
| 是否应继续原样推进 | 不应 |
| 推荐策略 | 保留蓝图，重构执行和验收体系 |

一句话总结：

> 方案知道“最终系统应该长什么样”，但当前执行体系还不能可靠证明“每一步真的做到了”。

# 三、当前实际执行缺陷

## 3.1 将“文件产出”误认为“阶段完成”

当前进度统计主要使用：

```text
15/15 文件完成
262 项测试通过
```

但这两个数字只能证明：

- 文件已经存在；
- 现有测试与现有实现之间没有冲突。

它们不能证明：

- 公共接口满足设计；
- 跨文件合同正确；
- 生命周期行为正确；
- 跨平台行为正确；
- 干净环境可安装；
- 回滚可执行；
- 集成链路可用；
- 数据迁移安全。

应区分：

```text
已生成
已实现
已单测
已合同验证
已集成
已验收
已灰度
已发布
```

任何一个文件仅完成前两项，都不能标记为“完成”。

## 3.2 测试通过不等于设计通过

当前测试存在以下典型问题：

- 没有真实执行方案要求的完整 `from core import ...`；
- 没有真实跨文件循环依赖测试；
- 没有错误码前缀反例测试；
- 没有异常自动注入 trace/span 测试；
- 没有 Windows 控制台事件测试；
- 没有生产日志采样测试；
- 没有干净虚拟环境安装测试；
- 没有 DTO 深层不可变测试；
- 没有 ISO 跨年周测试；
- 没有清理回调异常传播测试；
- 部分断言存在“永远为真”的写法；
- 部分所谓异常链测试没有真正验证 `__cause__`；
- 部分测试只验证字段存在，不验证设计要求的行为。

因此，现有测试更接近：

> 当前实现的回归保护。

而不是：

> 对执行方案的正式验收。

## 3.3 同一过程同时生成代码、测试和结论

当前执行方式容易形成以下闭环：

```text
同一个执行过程生成代码
→ 同一个执行过程生成测试
→ 同一个执行过程解释测试结果
→ 同一个执行过程宣布阶段完成
```

这种方式容易产生确认偏差：

- 测试按现有实现编写；
- 设计目标被实现细节替代；
- 边界条件被忽略；
- 错误标准被悄悄降低；
- 文档中的强要求被解释为“基本实现即可”；
- 测试通过后缺少独立反例审查。

必须把实现、对抗审查和验收拆开。

## 3.4 横向铺开过快，纵向验证过晚

原方案倾向于先批量生成完整底层模块，再逐步迁移上层。

这种方式结构整齐，但存在风险：

- DTO 在没有真实调用方时定义；
- Protocol 在没有实现方时冻结；
- 容器在没有完整启动链时设计；
- 日志和 trace 在没有请求链时验证；
- 配置热更在没有真实消费者时验证；
- 异常合同在没有跨层传播时验证。

结果可能是：

> 每个文件单独看都合理，但真实组合后接口不匹配。

因此，必须尽早建立一个最小纵向链路，用真实调用证明基础合同成立。

## 3.5 高风险审查名单过于固定

原方案提前指定少数 max 深审文件。这种做法有一定价值，但存在明显不足。

实际高风险模块不只包括：

- `types.py`
- `container.py`
- `exceptions.py`
- `signal_handler.py`

还包括：

- `config.py`
- `cache.py`
- `logging.py`
- `utils.py`
- `lint_imports.py`
- `requirements/`

特别是：

- lint 是架构门禁；
- config 是全项目运行参数真源；
- logging 涉及敏感信息；
- utils 的时间语义影响数据兼容；
- requirements 决定项目能否在干净环境运行；
- cache 涉及并发竞争。

深审范围必须根据实际风险动态调整，而不是预先固定文件数量。

## 3.6 过度依赖模型档位作为质量保证

方案使用 xhigh、ultracode、max 等档位区分批量生成和深度复核。

这可以作为执行提示，但不能成为验收标准。

以下推理不成立：

```text
使用 max 复核
=
文件已经可靠
```

真正的质量证据应包括：

- 合同测试；
- 失败反例；
- 并发测试；
- 故障注入；
- 类型检查；
- 静态分析；
- 集成测试；
- 跨平台测试；
- 性能基准；
- 回滚演练；
- 独立审查。

模型档位只能决定“如何工作”，不能决定“是否通过”。

## 3.7 lint 规则启用过晚

部分规则计划到较后阶段才启用，例如：

- 禁止运行期 resolve；
- 禁止裸异常；
- 禁止硬编码 URL；
- 禁止顶层 IO；
- DTO frozen 检查；
- 版本输出检查。

这些规则实际应尽早启用。

原则应为：

> 哪个合同在哪个阶段创建，保护该合同的规则就应在同一阶段启用。

建议：

| 规则 | 最迟启用阶段 |
|---|---|
| 真实循环依赖 | Phase 1 |
| SyntaxError 硬失败 | Phase 1 |
| DTO 不可变 | Phase 1 |
| 版本唯一真源 | Phase 1 |
| 禁止顶层 IO | Phase 1 |
| 禁止裸异常 | Phase 1 |
| 禁止硬编码 URL | Phase 1 |
| 禁止运行期 resolve | Phase 1 或 Phase 2 |
| 私有包保护 | 私有包首次出现时 |
| 层级依赖 | 每层首次出现时 |

## 3.8 灰度指标不够严谨

方案中常见指标：

```text
错误率 < 5%
差异率 < 10%
延迟 < 2x
输出 diff < 1%
```

这些数字存在问题。

### 错误率定义不清

必须区分：

- 崩溃；
- 5xx；
- 外部依赖失败；
- 降级响应；
- 业务拒绝；
- 用户输入错误；
- 数据一致性错误；
- 安全错误。

不能把它们合并成一个“错误率”。

### 自然语言输出不适合字符串 diff

LLM 输出可能语义一致但文字不同。应使用：

- 必要信息覆盖率；
- 结构字段一致性；
- 禁止内容检查；
- token 变化；
- 人工抽样；
- 语义评价；
- 业务任务完成率。

### 缺少最小样本量

“1% 流量”没有说明：

- 请求总数；
- 观察时长；
- 场景覆盖；
- 人工抽检数量；
- 错误预算。

没有最低样本要求，灰度结论可能没有统计意义。

## 3.9 有状态回滚设计不足

“特性开关切回旧链路”适合：

- LLM 调用；
- 无状态业务处理；
- 插件调度；
- Prompt 生成。

但不足以处理：

- 数据库 schema；
- 记忆写入；
- 索引；
- 状态快照；
- 数据文件；
- 双写；
- migration；
- 死信队列；
- 数据版本升级。

新版本如果已经写入新格式数据，切回旧代码后，旧版本未必能读取。

有状态回滚必须考虑：

- 数据主源；
- schema 双向兼容；
- 双写一致性；
- 写失败补偿；
- 幂等；
- 反向迁移；
- 灰度期数据处理；
- 索引重建；
- 数据校验和；
- 回滚演练。

## 3.10 文档与代码发生漂移

实际已经出现：

- 进度表说导出 33 个符号，代码并未做到；
- 方案要求 requirements 五组拆分，实际拆分不同；
- 方案要求真实循环依赖检测，实现未做到；
- 测试描述声称验证某项行为，实际测试并未验证；
- 进度状态显示完成，验收点却失败。

说明目前文档主要靠人工维护，缺少机器可验证的对应关系。

# 四、立即止损措施

在基础合同重新稳定前，暂停继续横向扩张。

建议执行：

```text
冻结新增模块
→ 保存当前代码基线
→ 修复 Phase 1 P0/P1
→ 建立正式验收测试
→ 跑通最小纵向链路
→ 重新审查 Phase 2.1
→ 再开始 Phase 2.2
```

## 4.1 允许进行的工作

- 修复 Phase 1；
- 补充验收测试；
- 补充 CI；
- 修复 Phase 2.1 对基础合同的引用；
- 建立迁移脚本；
- 建立回滚工具；
- 修正文档状态；
- 建立指标基线；
- 增加故障注入。

## 4.2 暂停进行的工作

- 新增 Phase 3 及以后模块；
- 大规模旧 import 替换；
- 删除旧实现；
- 不可逆数据库迁移；
- 大规模新旧链路切换；
- 继续按文件数量更新完成状态；
- 没有验证的并行批量生成。

# 六、为每个阶段建立四道硬门禁

## 6.1 实现门

验证：

- 文件存在；
- 代码可编译；
- import 成功；
- 类型检查通过；
- lint 基础规则通过；
- requirements 声明完整；
- 不存在占位实现；
- 不存在明显死代码；
- 不存在导入时网络请求或重型副作用。

推荐：

```bash
python -m compileall .
ruff check .
mypy core infra
```

## 6.2 合同门

验证实现是否符合冻结的设计合同。

Phase 1 应至少验证：

```python
from core import (
    settings,
    Result,
    BaijinBaseError,
    DependencyContainer,
    install_signal_handlers,
)
```

并验证：

- `__all__` 与公共合同一致；
- DTO 深层不可变；
- `Result` 不允许非法状态；
- Protocol 实现不匹配时失败；
- lazy 组件首次 resolve 自动 start；
- 容器发现缺失依赖；
- 容器发现递归循环；
- 启动失败自动回滚；
- 异常自动携带 trace/span；
- 错误码前缀强制；
- signal handler 跨平台；
- lint 发现真实循环；
- lint 对 SyntaxError 硬失败；
- 密钥 repr 符合合同；
- 生产日志采样存在；
- 版本来自唯一真源。

## 6.3 集成门

每阶段必须跑通真实纵向链路。

建议 Phase 1/2 最小链路：

```text
测试请求
→ trace middleware
→ service
→ DependencyContainer
→ LLM mock
→ database
→ Result
→ exception mapping
→ JSON logging
→ metrics
→ graceful shutdown
```

验证：

- trace 是否贯穿；
- config 是否被真实读取；
- 异常是否跨层转换；
- Result 是否能序列化；
- metrics 是否记录；
- 日志是否脱敏；
- 容器是否按依赖启动；
- shutdown 是否逆序停止。

## 6.4 发布门

必须满足：

- Linux CI；
- Windows CI；
- 干净环境安装；
- 无 P0/P1；
- 回滚演练；
- 灰度最低样本量；
- 文档与代码一致；
- 测试无核心 skip/xfail；
- 迁移可逆；
- 版本和构建信息可追踪。

# 七、建立“方案—实现—测试—证据”矩阵

每一条设计要求都必须有对应证据。

| 设计指标 | 实现位置 | 单元测试 | 合同测试 | 集成证据 | 当前状态 |
|---|---|---|---|---|---|
| core 公共导出 | `core/__init__.py` | facade test | import test | 真实入口使用 | 待修 |
| Protocol 校验 | `core/container.py` | provider test | bad impl test | service 注入 | 待修 |
| Windows 关闭事件 | `signal_handler.py` | mock test | Windows runner | launcher 关闭 | 缺失 |
| trace 自动注入 | `exceptions.py` | context test | exception contract | 请求链日志 | 缺失 |
| 循环依赖检测 | `lint_imports.py` | graph test | two-file cycle | CI lint | 待修 |
| 生产采样 | `logging.py` | sampling test | production config | 压测日志 | 缺失 |
| requirements | requirements | parser test | clean install | CI matrix | 待修 |

规则：

1. 每个设计指标必须有实现位置；
2. 每个指标必须有测试；
3. 每个测试必须含成功和失败样例；
4. 没有证据的指标不得完成；
5. 修改方案必须同步修改矩阵；
6. 测试名称必须对应合同；
7. 验收报告必须引用具体 commit。

# 八、采用失败测试优先

所有缺陷修复流程统一为：

```text
复现问题
→ 写失败测试
→ 证明旧实现失败
→ 修改实现
→ 证明新测试通过
→ 执行全量回归
→ 更新证据矩阵
```

## 8.1 真实循环依赖

构造：

```text
a.py -> import b
b.py -> import a
```

旧 lint 必须失败测试，新 lint 必须检出完整链路。

## 8.2 Protocol

构造不符合 Protocol 的实现，要求注册或启动失败。

## 8.3 lazy 生命周期

首次 resolve 后必须：

- 实例已创建；
- Protocol 已校验；
- `start()` 已执行；
- 并发下只执行一次。

## 8.4 shutdown 异常

清理回调抛异常时：

- 不能记录成功；
- 必须返回失败退出码；
- 仍应继续执行其他清理步骤；
- 最终聚合错误。

## 8.5 DTO 深层不可变

必须验证：

```python
dto.memories.append(...)
dto.extra["x"] = ...
dto.tags.append(...)
```

无法修改。

## 8.6 时间工具

必须验证：

- 标准 Unix 时间戳；
- 北京时区仅参与显示；
- 2021-01-01 为 2020-W53；
- 2018-12-31 为 2019-W01；
- 毫秒时间戳被拒绝；
- 远未来时间被拒绝。

# 十二、有状态回滚完善

```text
schema_to

finished_at

checksum_before
checksum_after
```

## 12.4 索引可重建


```text

→ 验证无重复

```

# 二十、最终结论

当前问题不需要推翻白槿 v2 的总体架构。

真正需要改变的是：

## 第一，从“产出了什么”改为“证明了什么”

不再以文件数量、代码行数、测试数量作为阶段完成的主要依据。

## 第二，从“实现回归测试”改为“设计合同和失败路径验证”

测试必须验证方案本身，并且包含反例。

## 第三，从“横向批量铺开”改为“小批次、纵向跑通、逐门验收”

先建立真实链路，再扩大模块范围。

## 第四，从“人工更新进度”改为“机器证据驱动状态”

进度表必须能够被代码、测试、CI 和验收报告验证。

## 第五，从“切回旧代码”改为“有状态可逆迁移”

数据库、索引、状态和文件必须有真正的回滚设计。

## 第六，从“指定少数文件深审”改为“按风险动态审查”

任何高风险模块都必须进入深审。

最终目标不是让方案看起来更完整，而是建立一个可靠闭环：

> 每一项设计要求都有实现，每一项实现都有测试，每一项测试都能失败，每一个阶段都有真实集成，每一次发布都能回滚，每一个完成状态都有证据。
