# 白槿 v2 开源优先代码审查系统建设方案

> 文档类型：代码审查基础设施、工程治理流水线与开源技术选型方案  
> 适用范围：白槿 v2 项目及后续由 Claude Code、Codex CLI、ChatGPT 参与的本地开发与审查流程  
> 适用对象：项目负责人、AI 开发者、审查者、测试维护者及后续接入的真人工程师  
> 核心目标：尽可能使用成熟开源技术搭建代码审查系统，自研部分仅保留白槿专属政策、工具输出适配和最终报告层  
> 建设原则：**审查系统的骨架采用成熟开源组件，项目只维护必要的薄胶水代码，不重新发明通用测试、静态分析、依赖检查、安全扫描和政策执行框架**

---

# 一、建设背景

白槿 v2 后续将大量依赖 AI 参与开发，包括：

- Claude Code 编写和修改代码；
- Codex CLI 进行独立审查；
- ChatGPT 对复杂改动进行深度复核；
- 本地 Git 记录真实变化；
- 自动测试和机器门禁决定是否允许进入下一阶段。

在此前的讨论中，已经确认以下事实：

1. 仅依赖 AI 口头汇报不可靠；
2. 仅依赖 `git diff` 不足以支撑完整工程审查；
3. 自己从零编写完整审查系统风险很高；
4. 审查系统本身也可能有错误；
5. 项目负责人不具备逐行阅读代码的能力；
6. GitHub 在中国大陆连接不稳定；
7. 当前预算主要是 ChatGPT Plus，不适合长期依赖额外 OpenAI API；
8. 审查系统需要能够本地运行、可中断恢复、低成本、逐步扩展。

因此，本方案不以“自研一个全新审查平台”为目标，而是采用：

```text
成熟开源工具
+
少量项目适配代码
+
Codex CLI 独立 AI 审查
+
本地 Git 和 Claude Code Hooks
```

组成一条可持续的本地审查流水线。

---

# 二、总体建设原则

## 2.1 开源优先

凡是已有成熟开源项目可以解决的问题，原则上不自行实现。

例如：

- 不自行实现代码格式检查器；
- 不自行实现类型分析器；
- 不自行实现 Python 依赖图算法；
- 不自行实现测试运行框架；
- 不自行实现密钥扫描器；
- 不自行维护漏洞数据库；
- 不自行设计通用政策语言；
- 不自行设计完整 Hook 管理框架；
- 不自行实现 Git diff 引擎；
- 不自行实现通用变异测试框架。

## 2.2 薄适配原则

项目自研部分只负责：

- 将多个工具的结果转换成统一 JSON；
- 定义白槿专属 P0/P1 规则；
- 定义白槿架构合同；
- 定义哪些改动必须人工确认；
- 定义数据库、密钥、权限和删除操作的红线；
- 将机器结果生成人可以理解的中文报告；
- 将 Claude Code、Codex CLI 和审查工具连接起来。

## 2.3 确定性工具优先于 AI

执行顺序必须是：

```text
确定性工具检查
↓
开源政策引擎裁决
↓
Codex CLI 深度审查
↓
政策引擎再次裁决
```

AI 审查只能作为附加层，不能替代：

- 编译；
- lint；
- 类型检查；
- 架构检查；
- 测试；
- 安全扫描；
- 密钥扫描；
- 依赖漏洞扫描；
- 政策门禁。

## 2.4 本地优先

考虑到网络和预算，第一阶段应尽量本地运行：

- 本地 Git；
- 本地 Nox；
- 本地 Ruff；
- 本地 mypy；
- 本地 Import Linter；
- 本地 pytest；
- 本地 Hypothesis；
- 本地 Gitleaks；
- 本地 OPA/Conftest；
- 本地 Codex CLI；
- Claude Code Hooks。

不把 GitHub、远程 CI 或公网 MCP 作为第一阶段的必要条件。

## 2.5 逐步扩展

不在第一天安装所有工具。

应分阶段完成：

```text
第一阶段：基础执行和政策门禁
第二阶段：安全与结果汇总
第三阶段：深度质量、可视化和变异测试
```

# 三、总体技术架构

推荐架构如下：

```text
Claude Code
    ↓

    ↓
pre-commit
    ↓
Nox
    ├── Ruff
    ├── mypy
    ├── Import Linter
    ├── pytest
    ├── Hypothesis
    ├── Gitleaks

    └── Semgrep / OpenGrep
    ↓
结果适配层
    ↓

    ↓
```

审查包至少包括：

```text

├── codex-review.json
├── policy-result.json
├── phase-status.yaml
└── final-report.md
```

# 四、核心开源组件选型

# 4.1 Git：真实改动与恢复基础

Git 是整个系统的事实来源之一。

负责：

- 记录所有文件修改；
- 区分新增、修改和删除；
- 生成 `git diff`；
- 生成改动文件清单；
- 建立修改前恢复点；
- 绑定审查结果与 commit；
- 支持失败后回退；
- 保存阶段历史。

推荐输出：

```bash
git diff --name-status
git diff --stat
git diff
git rev-parse HEAD
git status --porcelain
```

分别生成：

```text
changed-files.txt
diff-stat.txt
patch.diff
commit.txt
working-tree-status.txt
```

注意：

> `git diff` 是必要证据，但不能单独作为完整审查材料。

完整审查还必须包含：

- 任务目标；
- 修改后的完整文件；
- 测试结果；
- 架构上下文；
- 阶段状态；
- Codex 审查结果；
- 政策裁决结果。

---

# 4.2 pre-commit：本地提交前检查框架

`pre-commit` 负责管理本地 Git Hooks。

适合执行：

- Python 语法检查；
- YAML/TOML/JSON 格式检查；
- 文件末尾换行；
- 尾部空格；
- 大文件检查；
- Ruff；
- mypy 的轻量检查；
- Gitleaks；
- 自定义快速检查。

它应替代自研的：

- Hook 安装逻辑；
- Hook 调度；
- 文件过滤；
- 提交前命令管理。

需要注意：

> pre-commit 是提前反馈层，不是最终门禁，因为本地 Hook 可以被绕过。

最终裁决仍由 Nox、OPA/Conftest 和独立验收流程完成。

---

# 4.3 Nox：统一任务编排

Nox 应作为代码审查系统的统一执行入口。

它替代：

```text
run_tests.py
run_lint.py
run_security.py
run_architecture.py
run_all_checks.py
```

推荐会话：

```python
@nox.session
def lint(session):
    ...

@nox.session
def types(session):
    ...

@nox.session
def architecture(session):
    ...

@nox.session
def tests_unit(session):
    ...

@nox.session
def tests_contract(session):
    ...

@nox.session
def tests_integration(session):
    ...

@nox.session
def tests_policy(session):
    ...

@nox.session
def security(session):
    ...

@nox.session
def acceptance(session):
    ...
```

统一执行：

```bash
nox
```

或只运行指定任务：

```bash
nox -s lint types architecture
nox -s tests_unit tests_contract
nox -s security acceptance
```

Nox 的价值在于：

- 隔离检查环境；
- 固定运行顺序；
- 统一依赖；
- 降低本地环境污染；
- 让 Claude 和 Codex 使用同一套命令；
- 便于生成统一结果。

---

# 4.4 Ruff：格式与静态规则

Ruff 负责：

- Python 格式化；
- import 排序；
- 未使用 import；
- 未使用变量；
- 常见代码错误；
- 一部分复杂度规则；
- 一部分安全规则；
- 现代 Python 语法升级；
- 避免重复使用多个格式和 lint 工具。

建议避免同时堆叠：

```text
Black
isort
Flake8
pyupgrade
autoflake
```

对于个人项目，Ruff 可以承担上述大部分职责，降低工具冲突和维护成本。

推荐模式：

```bash
ruff format --check .
ruff check .
```

正式门禁中只检查，不自动修改。  
自动修改可由 Claude 在开发阶段执行：

```bash
ruff format .
ruff check --fix .
```

---

# 4.5 mypy：静态类型检查

mypy 负责：

- 函数参数类型；
- 返回值类型；
- Optional；
- Protocol；
- 泛型；
- DTO；
- Result；
- Repository 接口；
- async 函数；
- 容器提供者签名；
- 跨模块类型合同。

建议渐进式严格：

第一阶段：

```toml
warn_unused_ignores = true
warn_redundant_casts = true
check_untyped_defs = true
```

稳定后逐步增加：

```toml
disallow_untyped_defs = true
no_implicit_optional = true
strict_equality = true
```

不要一开始对整个历史项目开启最严格模式，否则可能产生大量噪声，导致团队通过忽略规则来“消灭红灯”。

---

# 4.6 Import Linter：架构和依赖合同

Import Linter 应替代自研的通用依赖图检查器。

它负责：

- 层级依赖；
- 禁止依赖；
- 独立模块；
- 保护模块；
- 循环依赖；
- sibling 模块约束；
- core 不得依赖 infra；
- domain 不得依赖 app；
- 私有包不得被外部访问。

示例：

```toml
[tool.importlinter]
root_package = "baijin"

[[tool.importlinter.contracts]]
name = "Core must not import infrastructure"
type = "forbidden"
source_modules = ["baijin.core"]
forbidden_modules = ["baijin.infra"]

[[tool.importlinter.contracts]]
name = "Layer order"
type = "layers"
layers = [
  "baijin.app",
  "baijin.services",
  "baijin.domain",
  "baijin.infra",
  "baijin.core",
]
```

项目只维护“依赖合同”，不维护：

- AST import 解析算法；
- 图构造；
- 环检测；
- 路径解析；
- 报告格式。

如果 Import Linter 无法覆盖某条极特殊规则，再补一个非常小的自定义检查，而不是保留完整自研依赖分析器。

---

# 4.7 pytest：测试执行核心

pytest 应作为所有行为验证的统一基础。

推荐目录：

```text
tests/
├── unit/
├── contracts/
├── integration/
├── acceptance/
├── fault_injection/
├── policy/
└── poisoned_cases/
```

职责划分：

## unit

测试单个函数或类。

## contracts

测试：

- 公共 import；
- DTO 不变量；
- Protocol；
- 异常合同；
- 配置合同；
- 生命周期合同。

## integration

测试跨模块真实连接。

## acceptance

测试阶段完成标准。

## fault_injection

测试：

- 启动失败；
- 回滚；
- DB locked；
- 日志不可写；
- 超时；
- 部分写入；
- 外部服务失败。

## policy

测试审查系统自身。

## poisoned_cases

放置已知错误的投毒样例，用于验证门禁能否阻止坏代码。

pytest 应输出 JUnit XML：

```bash
pytest --junitxml=artifacts/current/pytest.xml
```

政策系统只读取结构化结果，不解析散乱终端文本。

# 4.8 Hypothesis：属性和边界测试

Hypothesis 负责自动寻找边界输入和反例。

适合：

- 时间戳；
- Unicode；
- DTO 不变量；
- Result 合法状态；
- 配置解析；
- 序列化往返；
- 缓存状态；
- 路径处理；
- 状态机；
- 数值边界；
- 空集合和超长输入。

例如，测试 Result 的核心性质：

```text
成功结果必须有 value 且没有 error
失败结果必须有 error 且没有 value
序列化后再反序列化应保持等价
```

Hypothesis 能比手工列举几个样例更容易发现：

- 空值；
- 特殊字符；
- 极端长度；
- 跨年日期；
- 边界整数；
- 非法状态组合。

---

# 4.9 Gitleaks：密钥和凭证扫描

Gitleaks 负责扫描：

- API Key；
- Token；
- 私钥；
- 密码；
- 云平台凭证；
- `.env` 泄漏；
- Git 历史中的秘密。

它替代自研正则扫描器。

建议至少检查：

```bash
gitleaks detect --source . --no-banner
```

如果后续需要检查提交历史，可执行完整 Git 扫描。

Gitleaks 失败应视为强制阻断项。

---

# 4.10 pip-audit：依赖漏洞扫描

pip-audit 负责检查 Python 依赖中的已知漏洞。

它应检查：

- 当前环境；
- 锁文件；
- requirements；
- 直接和间接依赖。

依赖漏洞不能全部自动判定为 P0/P1，应结合：

- 漏洞严重性；
- 是否实际使用受影响功能；
- 是否存在修复版本；
- 是否暴露在外部输入路径；
- 是否有临时缓解措施。

但以下情况应直接阻断：

- 已知远程代码执行；
- 身份认证绕过；
- 密钥泄漏；
- 白槿实际调用受影响路径；
- 已有兼容修复版本但长期不升级。

---

# 4.11 Semgrep CE 或 OpenGrep：安全和项目规则

Semgrep/OpenGrep 负责：

- `eval`、`exec`；
- shell 注入；
- 不安全反序列化；
- 裸异常；
- 硬编码密码；
- 危险文件操作；
- 直接调用删除接口；
- 禁止的运行时 `container.resolve()`；
- 日志输出 SecretStr；
- 未经许可访问私有模块；
- 绕过安全包装器。

项目可以编写少量白槿专属规则，但不自行实现规则引擎。

建议第一阶段先不启用过多规则，以免产生大量误报。

第二阶段逐步加入：

```text
通用 Python 安全规则
+
白槿专属高风险规则
```

对许可证非常敏感时，可进一步评估 OpenGrep 或自维护规则集。

---

# 4.12 mutmut：测试有效性验证

mutmut 通过故意修改代码来判断测试是否真的能捕获错误。

例如它可能自动把：

```python
a > b
```

改成：

```python
a >= b
```

如果测试仍然全部通过，说明测试可能没有真正覆盖这一行为。

适合用于：

- Result 不变量；
- 生命周期；
- 错误码；
- 配置解析；
- 数据写入；
- 回滚逻辑；
- 安全判断；
- 时间边界。

由于 Windows 环境限制，建议：

- 第一版不强制；
- 后续通过 WSL 运行；
- 每周或每个 Phase 深度验收时运行；
- 不要求每次小改动都运行。

---

# 4.13 reviewdog：结果聚焦与统一展示

reviewdog 适合将多个工具的结果映射到文件和行，并聚焦本次新增问题。

它可以用于：

- Ruff；
- mypy；
- Semgrep；
- 自定义检查输出；
- 只显示本次 diff 新增的问题；
- 统一退出状态。

对于本地个人工作流，它可以减少海量历史问题对当前任务的干扰。

第一版可以先不用；当工具数量增加后再接入。

---

# 4.14 MegaLinter：可选的大规模整合层

MegaLinter 可统一运行大量 linter，并生成完整报告。

优点：

- 工具集成丰富；
- 统一配置；
- 统一结果目录；
- 适合多语言项目；
- 能提供较成熟的扫描体验。

缺点：

- 通常依赖 Docker；
- 镜像较大；
- 首次下载消耗流量；
- 对单一 Python 项目可能偏重；
- 与 Nox 编排存在重叠。

建议：

```text
第一版：Nox
后续多语言或工具扩张：再评估 MegaLinter
```

不要第一天同时上 Nox 和 MegaLinter。

---

# 4.15 SonarQube Community Build：可选仪表盘

SonarQube 可作为长期质量趋势和可视化平台。

适合：

- 技术债；
- 新代码问题；
- 质量门；
- 可维护性；
- 可靠性；
- 安全问题趋势；
- 项目负责人查看仪表盘。

但它不应成为唯一门禁。

原因：

- 部署较重；
- 资源占用高于 CLI 工具；
- 部分组件许可证需要额外评估；
- 对当前个人项目第一阶段不必要。

建议在系统稳定后作为可视化层增加。

# 五、OPA + Conftest：核心政策引擎

这是整个方案的核心。

不要让自研 `policy_gate.py` 逐步变成一个复杂、难以验证的政策框架。

应使用：

```text
Open Policy Agent
+
Conftest
```

OPA 负责根据结构化输入判断：

- 允许；
- 拒绝；
- 需要人工确认；
- 存在哪些政策违规。

Conftest 负责在命令行中运行这些政策。

# 六、统一审查输入

所有开源工具运行后，将结果整理成统一文件：

```text
artifacts/current/review-input.json
```

示例：

```json
{
  "metadata": {
    "task_id": "PHASE1-R1",
    "commit": "abc123",
    "policy_version": "1.0.0"
  },
  "changes": {
    "files_changed": 8,
    "files_added": 3,
    "files_deleted": 0,
    "database_changed": false,
    "security_files_changed": false,
    "policy_files_changed": false
  },
  "checks": {
    "compile": "pass",
    "ruff": "pass",
    "mypy": "pass",
    "import_linter": "pass",
    "pytest": {
      "passed": 312,
      "failed": 0,
      "skipped": 0
    },
    "gitleaks": "pass",
    "pip_audit": "pass",
    "semgrep": {
      "critical": 0,
      "high": 0,
      "medium": 2
    }
  },
  "defects": {
    "p0_open": 0,
    "p1_open": 0
  },
  "codex": {
    "safe_to_accept": true,
    "p0": 0,
    "p1": 0,

```

自研适配层只负责：

- 读取工具结果；
- 转成统一字段；
- 不负责决定通过或失败。

# 七、OPA 政策示例

```rego
package baijin.review

deny contains "P0 defect exists" if {
    input.defects.p0_open > 0
}

deny contains "P1 defect exists" if {
    input.defects.p1_open > 0
}

deny contains "Compile failed" if {
    input.checks.compile != "pass"
}

deny contains "Ruff failed" if {
    input.checks.ruff != "pass"
}

deny contains "Type check failed" if {
    input.checks.mypy != "pass"
}

deny contains "Architecture contract failed" if {
    input.checks.import_linter != "pass"
}

deny contains "Tests failed" if {
    input.checks.pytest.failed > 0
}

deny contains "Secret detected" if {
    input.checks.gitleaks != "pass"
}

deny contains "Critical security finding" if {
    input.checks.semgrep.critical > 0
}

deny contains "AI review rejected change" if {
    input.codex.safe_to_accept == false
}

require_human contains "Database migration changed" if {
    input.changes.database_changed == true
}

require_human contains "Security policy changed" if {
    input.changes.security_files_changed == true
}

require_human contains "Governance policy changed" if {
    input.changes.policy_files_changed == true
}
```

运行：

```bash
conftest test artifacts/current/review-input.json
```

退出码非零：

```text
门禁失败
```

需要人工确认时：

```text
不自动通过
```

# 八、Codex CLI 的职责

Codex CLI 不是基础扫描器，而是深度审查层。

它负责发现：

- 设计偏离；
- 生命周期错误；
- 并发问题；
- 异常传播问题；
- 测试与设计不一致；
- 测试虽然通过但无法证明目标；
- 回滚不完整；
- 数据一致性风险；
- 跨模块隐含影响；
- 文档与代码漂移；
- 业务语义错误。

Codex 应使用：

```text
read-only sandbox
```

只读审查，不能修改 Claude 的代码。

结构化输出示例：

```json
{
  "decision": "changes_required",
  "safe_to_accept": false,
  "p0": [],
  "p1": [
    {
      "file": "core/container.py",
      "line": 126,
      "problem": "启动失败后没有逆序回滚已启动组件",
      "required_fix": "记录已启动组件，并在异常时逆序停止"
    }
  ],
  "p2": [],
  "missing_tests": [
    "第三个组件启动失败时的回滚测试"
  ],
  "policy_violations": [],
  "test_result_consistent": true
}
```

随后将该结果加入 `review-input.json`，再次由 OPA 裁决。

# 九、Claude Code Hooks 的职责

Claude Code Hook 不负责实现审查逻辑，只负责触发成熟工具。

任务结束时：

```text
Claude Stop
↓
运行 Nox
↓
收集 Git 证据
↓
构建 review-input.json
↓
运行 Conftest
↓
调用 Codex CLI
↓
再次运行 Conftest
↓
生成 final-report.md
```

如果失败，Hook 返回：

```json
{
  "decision": "block",
  "reason": "审查系统发现 2 个 P1，请读取 artifacts/current/final-report.md 后继续修复。"
}
```

如果通过，允许 Claude 结束。

必须限制自动循环：

```yaml
max_repair_cycles: 2
max_changed_files: 20
stop_on_p0: true
require_user_on_database_change: true
require_user_on_security_change: true
require_user_on_policy_change: true
```

# 十、审查系统自身如何验证

审查系统不能因为采用了开源项目就默认正确。

必须建立：

```text
tests/policy/
tests/poisoned_cases/
```

至少包含以下投毒样例。

## 10.1 好样例

完整合法项目必须通过。

## 10.2 SyntaxError

必须失败。

## 10.3 真实循环依赖

必须被 Import Linter 拦截。

## 10.4 P0 未关闭

OPA 必须拒绝。

## 10.5 P1 未关闭

OPA 必须拒绝。

## 10.6 失败测试被 skip

政策必须拒绝或要求人工确认。

## 10.7 永真断言

例如：

```python
assert condition or True
```

必须被 Ruff、Semgrep 自定义规则或受保护测试发现。

## 10.8 密钥泄漏

Gitleaks 必须失败。

## 10.9 Codex 拒绝

`safe_to_accept=false` 时 OPA 必须拒绝。

## 10.10 工具结果缺失

缺少测试报告、Codex 报告或架构结果时必须：

```text
fail closed
```

不得默认通过。

## 10.11 OPA 政策异常

政策解析失败或 Conftest 异常必须失败。

## 10.12 修改政策文件

必须自动要求人工确认。

只有系统能够稳定做到：

```text
好样例能过
坏样例能拦
自身异常会失败
```

才允许用于真实 Phase 审查。

# 十七、风险与注意事项

## 17.1 工具越多不等于越安全

工具过多可能导致：

- 配置冲突；
- 重复报告；
- 大量误报；
- 运行时间增加；
- Claude 为消除噪声而随意加 ignore；
- 项目负责人无法理解结果。

因此应坚持：

```text
第一阶段少而精
稳定后再逐步增加
```

## 17.2 OPA 政策仍需测试

OPA 是成熟引擎，但白槿编写的 Rego 政策仍可能错误。

必须为每条政策提供：

- 正例；
- 反例；
- 缺失字段；
- 边界条件；
- 异常输入。

## 17.3 AI 不能作为唯一门禁

即使 Codex 判断通过，只要确定性工具失败，最终仍应失败。

## 17.4 不要把所有历史问题一次变成阻断项

如果历史项目已有大量 lint 或类型问题，应采用：

```text
禁止新增问题
+
逐步偿还旧问题
```

而不是第一天要求整个项目全部达到最高标准，导致门禁被关闭。

## 17.5 Windows 兼容性

部分工具在 Windows 上运行良好，但 mutmut 更适合通过 WSL。  
第一版应优先使用原生 Windows 兼容工具。

# 十九、最终结论

白槿 v2 的代码审查系统不应成为另一个需要大量自研、长期维护和反复修复的大型项目。

正确方向是：

> 使用成熟开源组件承担代码格式、静态分析、类型检查、架构依赖、测试执行、属性测试、安全扫描、密钥扫描、漏洞扫描和政策裁决；项目自身只编写必要的薄适配、白槿专属规则和中文报告。

最关键的三项选择是：

1. **Nox**：作为统一执行和环境编排层；
2. **OPA + Conftest**：作为正式政策裁决层；
3. **Ruff + mypy + Import Linter + pytest + Hypothesis + Gitleaks + Semgrep/OpenGrep**：作为确定性检查基础。

Codex CLI 的定位是：

```text
深度独立审查
```

而不是：

```text
替代全部开源工具
```

最终合理比例应为：

```text
85%～95% 成熟开源组件
+
5%～15% 白槿专属适配、政策和报告
```

这样才能真正建立一套：

- 可验证；
- 可维护；
- 可扩展；
- 低成本；
- 本地可运行；
- 不依赖 GitHub；
- 不依赖额外 OpenAI API；
- 适合个人项目负责人的代码审查系统。
