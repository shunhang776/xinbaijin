# 从 AI 编程到可信工程体系 —— 白槿 v2 工程治理实践总结

> 文档类型：AI 编程协作、工程治理与可信系统建设总结  
> 适用范围：白槿 v2 项目及其他大量使用 AI 参与开发的工程项目  
> 适用对象：项目负责人、AI 开发者、审查者、测试负责人、发布负责人及治理人员  
> 核心目标：在项目负责人不深入阅读代码、AI 可能犯错或不遵守规则的情况下，仍然通过权限隔离、机器门禁、独立审查、证据链和可恢复设计保证项目可靠推进

---

# 一、文档目的

本文档用于总结白槿 v2 项目在执行方案审查、工程治理、防腐机制、AI 协作开发以及可信工程体系建设过程中形成的核心思想。

本文不是代码规范，也不是单纯的项目管理文档。

本文回答的是一个更根本的问题：

> 当项目大量依赖 AI 开发，而项目负责人又不具备深入阅读代码能力时，如何确保项目仍然能够可靠、可控、可验证地推进？

---

# 二、问题的起点与演化

最初的问题看似简单：

```text
如何保证执行方案真正落地？
```

随后逐步演化为：

```text
如何防止政策腐化？
↓
如何建立强制约束？
↓
如果 AI 不遵守怎么办？
↓
如果项目负责人看不懂代码怎么办？
↓
如何构建一个即使 AI 不可信也能正常运行的系统？
```

最终发现：

真正的问题不是代码本身。

真正的问题是：

```text
信任
```

项目到底应该相信：

- AI；
- 开发者；
- 审查者；
- 测试；
- 文档；
- 还是系统机制。

最终结论是：

> 不应把工程信任建立在个人或 AI 的承诺上，而应建立在权限隔离、机器验证、独立审查、证据链和可恢复能力上。

---

# 三、为什么单纯依靠文档一定会失败

工程领域有一个普遍规律：

```text
文档 ≠ 执行
```

即使拥有：

- 执行方案；
- 缺陷补救方案；
- 工程政策防腐机制；
- 验收清单；
- 风险说明；

仍然可能出现：

```text
文档写得很好
↓
没人严格执行
↓
规则不断被解释和绕过
↓
风险被隐藏
↓
阶段继续标绿
↓
项目最终失控
```

原因很简单：

> 文档不会自动执行自己，也不会自动阻止违规操作。

因此，文档只能作为规则来源，不能成为唯一的执行保障。

---

# 四、工程政策常见的腐化方式

## 4.1 结果腐化

把：

```text
文件已生成
```

解释为：

```text
功能已完成
```

实际可能只是代码存在，但没有通过合同、集成、故障和回滚验证。

## 4.2 证据腐化

把：

```text
AI 说测试通过
```

解释为：

```text
测试真的通过
```

如果没有真实命令、真实日志、真实环境和对应 commit，这种说法不构成工程证据。

## 4.3 例外腐化

```text
临时绕过
↓
长期绕过
↓
默认绕过
```

当例外没有到期时间、责任人和移除计划时，规则最终会被彻底掏空。

## 4.4 权力腐化

最危险的结构是同一个主体同时负责：

```text
写代码
+
写测试
+
修改规则
+
解释结果
+
宣布通过
+
发布生产
```

在这种结构下，任何制度都可能被绕过。

## 4.5 指标腐化

例如：

- 用测试数量替代测试有效性；
- 用文件数量替代工程完成度；
- 用平均延迟掩盖 P99；
- 用“没有收到投诉”替代真实质量；
- 用“没有报错”替代故障注入和恢复能力。

## 4.6 文档腐化

文档中的状态、测试数量、导出符号、依赖关系和实际代码不一致，但仍被作为项目决策依据。

# 五、正确的工程治理思路

错误的依赖方式是：

```text
认真
负责
职业道德
AI 的承诺
开发者自觉
```

正确的依赖方式是：

```text
权限隔离
+
自动门禁
+
机器证据
+
独立审查
+
可恢复设计
```

核心原则是：

> 不要要求执行者永远正确，而要让错误难以进入正式系统；即使进入，也必须能够被快速发现、限制影响并恢复。

---

# 六、从制度治理转向技术治理

真正有效的制度必须变成：

```text
规则
↓
任务
↓
脚本
↓
门禁
↓
证据
↓
验收
```

而不是：

```text
规则
↓
阅读
↓
口头承诺
↓
自觉遵守
```

只有当违反规则会自动产生以下后果时，规则才具备真正约束力：

```text
CI 失败
PR 无法合并
阶段无法验收
制品无法签名
正式环境拒绝部署
灰度自动停止
```

---

# 七、五层强制治理体系

## 7.1 第一层：提交门禁

主分支必须受保护。

禁止：

```text
直接 push main
force push
删除主分支
未经审查合并
自我批准
```

标准流程：

```text
功能分支
↓
Pull Request
↓
CI
↓
独立 Review
↓
Merge
```

本地 Git Hook 只能用于提前提示，不能作为最终强制机制，因为它可以被 `--no-verify` 绕过。

## 7.2 第二层：合并门禁

建立统一的：

```text
policy-gate
```

至少检查：

- P0、P1 缺陷；
- 编译；
- lint；
- 类型检查；
- 公共合同测试；
- 集成测试；
- 跨平台测试；
- 例外是否过期；
- 验收报告是否匹配当前 commit；
- 核心测试是否被删除或弱化；
- 当前阶段是否满足进入下一阶段的条件。

只要门禁失败：

```text
PR 无法合并
```

门禁自身发生异常时也必须失败，即采用：

```text
fail closed
```

而不是“检查工具坏了，暂时放行”。

## 7.3 第三层：验收门禁

必须遵守：

```text
实现者 ≠ 最终验收者
```

关键模块必须独立审查，包括：

- 公共 DTO；
- 依赖注入容器；
- 生命周期；
- 数据迁移；
- 日志脱敏；
- 权限和密钥；
- 发布流水线；
- 回滚机制。

即使项目只有一个人，也应使用不同会话、不同上下文和不同任务目标完成实现、对抗审查和验收。

## 7.4 第四层：发布门禁

正式环境只接受：

```text
可信 CI 构建
+
指定 commit
+
通过 policy-gate
+
已签名制品
```

禁止：

```text
本地直接部署
本地重新打包
手工复制文件到生产
使用未验收 commit
```

正式环境不应接受开发者本地构建的制品。

## 7.5 第五层：运行时门禁

即使代码已经通过验收，运行时仍然需要自动保护。

例如：

```text
1% 灰度
↓
指标正常
↓
10%
↓
指标正常
↓
50%
↓
100%
```

出现以下情况时自动停止：

- 数据丢失；
- 安全事件；
- schema 不一致；
- 未处理异常超阈值；
- 回滚制品不可用；
- 关键指标缺失；
- 错误率显著高于旧版本。

触发后：

```text
停止扩流
→ 自动回退
→ 锁定发布
→ 保存现场
→ 创建事故记录
```

# 八、默认 AI 不可信

整个讨论最重要的转折点是：

> 如果 AI 根本不遵守制度怎么办？

正确答案不是继续要求 AI：

```text
请严格遵守
请认真检查
请不要漏掉
```

而是：

```text
默认 AI 不可信
```

然后基于这个前提设计系统。

---

# 九、AI 的正确角色：候选补丁生成器

AI 可以负责：

```text
编写候选代码
编写基础测试
生成修改说明
提出风险
提出修复方案
```

AI 不应该拥有：

```text
修改最终政策
修改独立门禁
批准自己的 PR
获取生产密钥
直接部署生产
运行正式数据库迁移
删除审计记录
宣布阶段正式通过
```

AI 即使完全不遵守文档，也最多只能生成一个不合格补丁，而不能把它直接送进生产系统。

# 十、可信工程体系架构

推荐架构：

```text
AI Worker
↓
Isolated Sandbox
↓
External Governance Gate
↓
Protected Merge
↓
Trusted Builder
↓
Release Controller
↓
Production
```

各部分职责如下。

## 10.1 AI Worker

- 读取项目代码；
- 在隔离分支生成候选修改；
- 无治理写权限；
- 无正式密钥；
- 无主分支写权限；
- 无发布权限。

## 10.2 Isolated Sandbox

- 运行候选代码；
- 限制网络和资源；
- 不包含生产凭证；
- 出错时不影响正式环境。

## 10.3 External Governance Gate

- 读取冻结政策；
- 运行独立验收测试；
- 检查缺陷、例外和证据；
- AI 不得修改。

## 10.4 Protected Merge

- 所有 required checks 通过；
- 独立审批完成；
- 禁止自我批准；
- 禁止管理员随意绕过。

## 10.5 Trusted Builder

- 从指定 commit 构建；
- 生成制品哈希；
- 保存构建来源；
- 使用受保护密钥签名。

## 10.6 Release Controller

- 验证制品签名；
- 执行灰度；
- 监控红线；
- 自动停止和回滚。

## 10.7 Production

- 只接受合法签名制品；
- 不接受本地构建；
- 不直接暴露凭证给 AI。

# 十一、治理仓库与业务仓库分离

不能把业务代码和强制治理代码全部放在 AI 可修改的同一个仓库中。

否则 AI 可以直接修改门禁，例如：

```python
def policy_gate():
    return True
```

推荐拆分为两个仓库。

## 11.1 业务仓库

包含：

```text
业务代码
普通测试
项目文档
开发脚本
```

AI 可以在受限分支修改。

## 11.2 治理仓库

包含：

```text
强制政策
独立验收测试
安全检查
发布规则
迁移检查器
门禁程序
```

AI 对治理仓库：

- 只读；
- 无提交权限；
- 无审批权限；
- 无修改发布规则权限。

业务仓库的 CI 调用治理仓库的固定版本和固定哈希，而不是调用当前业务分支中可以被修改的检查器。

---

# 十二、测试体系分层

如果 AI 能看到并修改全部验收测试，它可能：

- 删除失败用例；
- 弱化断言；
- 添加 `or True`；
- 添加 skip；
- 针对已知样例硬编码结果。

因此测试应分为两层。

## 12.1 公开开发测试

```text
tests/unit/
tests/integration/
```

用途：

- 快速开发；
- 回归保护；
- 帮助 AI 修复普通问题。

AI 可以读取和修改，但修改必须被审查。

## 12.2 受保护验收测试

```text
governance-tests/
  contract/
  security/
  migration/
  rollback/
  adversarial/
```

用途：

- 最终验收；
- 对抗性验证；
- 防止迎合公开测试；
- 检查政策是否真正落实。

AI 不得修改这些测试。

其中一部分边界输入和对抗场景可以不直接暴露给代码生成过程。

---

# 十三、验收结果必须由外部系统生成

AI 的陈述：

```text
所有测试已经通过
```

不应具有任何权限意义。

真正的验收状态只能由外部系统计算：

```yaml
commit: abc123
policy_bundle: e94f...
public_tests: pass
protected_contract_tests: pass
security_tests: pass
windows_tests: pass
linux_tests: pass
clean_install: pass
rollback_test: pass
p0_open: 0
p1_open: 0
accepted: true
```

其中：

```text
accepted
```

不能由 AI 或人工填写，而必须由确定性逻辑生成。

---

# 十四、构建与发布必须分离

必须防止：

```text
CI 验证的是代码 A
实际部署的是本地代码 B
```

可信构建流程应为：

```text
指定 commit
→ 可信构建环境
→ 外部门禁
→ 构建制品
→ 计算哈希
→ 生成来源证明
→ 签名
→ 保存不可变制品
```

生产环境只接受：

- 来源可信；
- commit 一致；
- policy-gate 通过；
- 签名有效；
- 哈希未变化；
- 未被撤销的制品。

AI 没有签名密钥，因此不能自行伪造正式制品。

---

# 十五、生产凭证必须与 AI 隔离

AI 运行环境中不得存在：

```text
生产数据库密码
SSH 密钥
云管理员令牌
正式 API 密钥
制品签名密钥
发布凭证
备份删除权限
```

不要试图通过提示词阻止 AI 滥用密钥。

正确方式是：

> 从一开始就不要让 AI 拥有密钥。

可信流水线应使用：

- 短期凭证；
- 最小权限；
- 指定环境；
- 指定操作；
- 完整审计；
- 不可导出。

---

# 十六、数据库迁移必须由独立控制器执行

AI 可以生成：

```text
up migration
down migration
precheck
postcheck
数据影响说明
```

但不能直接运行正式迁移。

迁移控制器必须检查：

- 迁移清单完整；
- 版本连续；
- 备份完成；
- precheck 通过；
- 副本环境演练通过；
- 数据校验通过；
- 回滚或前向修复路径存在；
- 独立审批完成；
- 应用版本兼容。

满足条件后，控制器才临时获得数据库权限执行。

---

# 十七、审计日志必须追加式保存

如果 AI 或开发者能够修改历史，就可能出现：

```text
测试失败
→ 删除失败报告
→ 重新生成成功报告
→ 声称从未失败
```

因此关键记录必须只能追加：

- CI 结果；
- 政策版本；
- 例外记录；
- 阶段状态；
- 构建哈希；
- 发布记录；
- 回滚记录；
- 迁移记录；
- 审批记录。

失败记录不能被覆盖，只能在后续提交中产生新的修复记录。

审计记录最好保存在业务仓库以外的系统中。

---

# 十八、针对 AI 绕过方式的根治措施

| AI 可能采取的行为 | 根治措施 |
|---|---|
| 不遵守文档 | 文档不负责执法，外部门禁执法 |
| 删除测试 | 关键测试存放在治理仓库 |
| 弱化断言 | 独立验收测试不受其控制 |
| 修改 policy gate | policy gate 不在其写权限内 |
| 谎称测试通过 | 系统自行执行并生成结果 |
| 手工标记完成 | 状态由门禁计算 |
| 直接修改主分支 | AI 身份无该权限 |
| 自我批准 PR | 权限规则禁止 |
| 直接部署 | AI 无生产凭证 |
| 自行打包制品 | 生产只接受可信签名制品 |
| 修改迁移记录 | 迁移控制器与审计系统独立 |
| 绕过灰度 | 发布控制器禁止越级 |
| 隐瞒失败 | 审计日志不可覆盖 |
| 修改 CI 配置 | 根配置位于受保护治理仓库 |
| 尝试读取秘密 | AI 环境中不保存正式秘密 |

# 十九、项目负责人不懂代码怎么办

结论是：

> 项目负责人不需要看懂每一行代码，但不能因此只能相信 AI。

项目负责人的职责是判断：

- 功能目标；
- 风险边界；
- 数据是否允许修改；
- 哪些问题不可接受；
- 是否允许进入下一阶段；
- 是否允许发布。

技术系统和独立审查负责判断：

- 代码能否运行；
- 合同是否满足；
- 是否有循环依赖；
- 并发是否安全；
- 测试是否有效；
- 是否可以回滚。

# 二十、项目负责人需要看懂的五张表

## 20.1 功能验收表

回答：

- 功能是否符合需求；
- 哪些功能已经完成；
- 哪些功能仍未完成。

## 20.2 缺陷表

回答：

- P0 是否为 0；
- P1 是否为 0；
- 是否存在已知高风险问题。

## 20.3 数据影响表

回答：

- 是否修改数据库；
- 是否删除或迁移数据；
- 是否可能影响用户数据；
- 是否已备份。

## 20.4 回滚表

回答：

- 出错后如何恢复；
- 是否真实演练；
- 恢复需要多久；
- 是否会丢失灰度期间的数据。

## 20.5 权限表

回答：

- AI 能做什么；
- 开发者能做什么；
- CI 能做什么；
- 谁能批准发布；
- 谁拥有生产密钥。

这五张表比阅读数千行代码更适合非技术项目负责人。

# 二十一、项目负责人应看到的人话验收报告

系统应自动生成项目负责人可以理解的报告，例如：

```markdown
# 本次变更验收摘要

## 修改目的

恢复 Phase 1 公共接口和容器生命周期合同。

## 实际改变

- 补充 core 公共导出；
- 增加合同测试；
- 修改容器生命周期；
- 未修改生产数据库；
- 未改变用户数据格式。

## 风险

- 中风险：可能影响旧导入路径；
- 无不可逆数据迁移；
- 无生产密钥变更。

## 验证结果

- 编译：通过；
- 原有回归测试：通过；
- 新合同测试：通过；
- Linux：通过；
- Windows：通过；
- 干净安装：通过；
- 故障注入：通过；
- 回滚演练：通过。

## 缺陷

- P0：0；
- P1：0；
- P2：2，已进入后续计划。

## 结论

允许合并，可以进入下一批整改。
```

摘要必须自动关联机器证据，不能由 AI 手工填绿。

# 二十二、不能只使用一个 AI

当项目负责人看不懂代码时，单一 AI 的错误更难被发现。

至少应采用三层验证。

## 22.1 实现 AI

负责：

- 编写代码；
- 编写基础测试；
- 说明修改；
- 说明已知风险。

没有最终决定权。

## 22.2 独立审查 AI

使用独立会话或不同模型，负责：

- 找 bug；
- 检查偏离方案；
- 检查无效测试；
- 构造失败场景；
- 检查假完成；
- 检查安全和回滚。

## 22.3 确定性机器检查

真实执行：

- 编译；
- lint；
- 单元测试；
- 合同测试；
- 集成测试；
- 干净安装；
- 跨平台测试；
- 数据迁移检查；
- 回滚演练。

即使两个 AI 都认为没有问题，只要机器检查失败，仍然不得通过。

---

# 二十三、高风险环节仍需真人审查

必须承认一个现实边界：

> 如果项目涉及真实用户、隐私、金钱、权限或不可恢复数据，仅靠多个 AI 和自动测试仍不能提供绝对安全保证。

以下变更应增加独立真人工程师审查：

- 数据库 schema；
- 大规模数据迁移；
- 身份验证和权限；
- API 密钥和安全；
- 自动更新；
- 文件删除；
- 生产发布系统；
- 备份和恢复；
- 远程代码执行；
- 用户隐私数据。

可以按风险分级：

```text
低风险：
AI 实现
+ 自动测试
+ 独立 AI 审查

中风险：
AI 实现
+ 独立 AI 审查
+ 强制 CI
+ 故障注入
+ 测试环境验证

高风险：
AI 实现
+ 外部验收测试
+ 强制 CI
+ 回滚演练
+ 小流量灰度
+ 独立真人审查
```

# 二十四、限制事故影响比证明代码完美更重要

无法证明代码绝对没有错误，因此必须保证错误不会造成灾难。

需要做到：

- AI 没有生产密钥；
- 自动备份；
- 发布前创建恢复点；
- 新功能默认关闭；
- 先在测试环境运行；
- 再开放少量流量；
- 数据写入尽量可撤销；
- 索引可重建；
- 日志不包含密钥；
- 出错自动回退；
- 开发和生产环境隔离。

目标不应是：

```text
保证 AI 永远不写错
```

而应是：

```text
AI 写错时
→ 错误进不了正式环境

即使进入
→ 只影响很小范围

出现问题
→ 能快速恢复
```

# 二十五、Claude Code 与 ChatGPT 的协作模式

为了避免 Claude Code 只用一句：

```text
已经完成
```

作为交付，应建立自动交接包。

推荐结构：

```text
review-package.zip
├── changed-files.txt
├── patch.diff
├── test-report.xml
├── phase-status.yaml
├── defects.yaml
├── exceptions.yaml
└── acceptance-report.md
```

# 二十六、审查包生成流程

推荐流程：

```text
Claude Code 写代码
↓
Hook 记录文件变化
↓
Git 生成真实 diff
↓
自动运行测试
↓
保存测试结果
↓
生成 review-package.zip
↓
终端显示压缩包路径
↓
用户上传给 ChatGPT
↓
ChatGPT 独立审查
```

文件清单和差异应来自 Git，而不是来自 Claude 的口头描述。

这样可以发现：

- Claude 漏报的文件；
- 意外删除；
- 测试被弱化；
- 政策文件被修改；
- 文档与代码不一致。

# 二十七、Claude Code 与 ChatGPT 的职责分工

## Claude Code

负责：

```text
开发
修改
运行本地测试
生成候选交付物
```

## ChatGPT

负责：

```text
独立审查
架构检查
测试真实性检查
政策合规检查
P0/P1 问题识别
回滚能力审查
文档与代码一致性审查
```

标准闭环：

```text
Claude 开发
↓
生成审查包
↓
ChatGPT 审查
↓
输出问题清单
↓
Claude 修复
↓
重新生成审查包
↓
再次审查
↓
机器门禁最终验收
```

这相当于：

```text
开发
↓
QA
↓
修复
↓
再审查
↓
验收
```

# 二十八、Claude Code 是否能直接把文件发给 ChatGPT

Claude Code 可以通过 Hook 自动：

- 记录刚写的文件；
- 收集 Git diff；
- 运行测试；
- 生成 ZIP；
- 在终端显示 ZIP 路径；
- 自动打开文件所在目录。

但当前两个聊天窗口之间通常不能直接互相推送文件。

现实可行的半自动流程是：

```text
Claude 自动生成 ZIP
↓
自动显示并打开目录
↓
用户把 ZIP 上传到 ChatGPT
```

用户只需要完成最后一次上传，不需要手工寻找每个文件，也不需要阅读代码。

# 二十九、个人项目的现实边界

如果项目完全由一个人掌握所有管理员权限，那么这个人理论上仍然可以关闭全部门禁。

因此个人项目无法做到绝对意义上的“连项目所有者自己都无法绕过”。

但可以显著提高绕过成本：

- 使用日常开发身份和治理身份；
- 日常身份无管理员权限；
- 治理身份使用硬件安全密钥；
- 治理仓库单独存放；
- 正式密钥不保存在开发电脑；
- 高风险操作延迟生效；
- 使用外部不可变备份；
- 高风险操作要求第二方批准。

# 三十、关于彻底解决问题的诚实边界

不存在一个可以保证所有 AI、所有人、所有软件和所有管理员永远不违规的绝对系统。

任何系统最终都会依赖某些可信根：

- 代码托管平台；
- 身份系统；
- CI 服务；
- 签名密钥；
- 操作系统；
- 硬件；
- 最终管理员。

如果控制可信根的人故意破坏规则，仍然可能造成问题。

因此工程上的“根治”不是消灭一切可能，而是：

1. 默认不信任 AI；
2. 不给 AI 关键能力；
3. 把执法放在 AI 之外；
4. 拆分关键权力；
5. 使用确定性系统验证；
6. 让绕过必须同时攻破多个独立控制面；
7. 让所有绕过留下不可删除的证据；
8. 保证系统能够恢复。

这已经从口头承诺提升为：

```text
能力级约束
```

# 三十二、最终形成的三条核心原则

## 原则一

> 不要相信 AI 的汇报，只相信机器实际执行并保存的证据。

## 原则二

> 不要要求 AI 守规矩，而要让 AI 即使不守规矩，也无法造成越权结果。

## 原则三

> 不要让任何一个 AI 或任何一个人同时拥有以下全部权力：

```text
写代码
+
修改规则
+
宣布通过
+
发布生产
```

# 三十三、最终结论

工程可靠性的根源，不是优秀的 AI，也不是永远不会犯错的人。

真正可靠的基础是：

```text
权限隔离
+
自动门禁
+
机器证据
+
独立审查
+
可信构建
+
运行时保护
+
可恢复系统
+
不可覆盖的审计链
```

成熟的工程体系应当做到：

```text
即使 AI 出错
↓
错误被发现或阻断

即使开发者偷懒
↓
门禁拒绝通过

即使审查遗漏
↓
运行时限制影响

即使发布失败
↓
系统可以回滚

即使项目负责人不懂代码
↓
仍能依据真实证据作出决策
```

最终要实现的是：

> 从“相信人和 AI”，转变为“相信由权限、证据、门禁和恢复能力共同构成的系统”。
